## 1. 目的と位置づけ

### 1.1 ISE-FS の目的

ISE-FS は以下を同時に満たすための**ファイルシステム論理層**である。

- **復号可能性の否定**
    
- **真正性のみの保証**
    
- **漏洩前提での安全性**
    
- **証跡（Witness）との完全整合**
    
- **分散・複製・再封緘に耐える**
    

> ISE-FS は「秘密を守る」ためのFSではない  
> **「真実が一つしか存在しない」ことだけを保証するFSである**

---

## 2. 設計原則（絶対条件）

### 2.1 基本原則

|原則|内容|
|---|---|
|復号否定|正しい鍵でも意味的復元は不可能|
|署名唯一|正当性は署名のみで確定|
|可搬性|ローカル / USB / NFS / S3 等で同一|
|再封緘|複製時に必ず再 ISE|
|非信頼|OS / 管理者 / 運用者を信用しない|

## 3. ISE-FS の論理レイヤ構成

`flowchart TB     A[Logical File] --> B[Chunker]     B --> C[ISE Transform]     C --> D[Compression]     D --> E[AES-GCM Seal]     E --> F[ISE Envelope]     F --> G[ISE-FS Storage]`

---

## 4. ファイル単位設計

### 4.1 ファイルの定義

ISE-FS における「ファイル」は以下の集合体である。

`ISEFile := {   Header,   Chunk[N],   Envelope[N],   Manifest }`

### 4.2 Header（非秘匿）

|Field|Size|説明|
|---|---|---|
|magic|8B|`ISEFSv1`|
|version|u16|FS version|
|flags|u16|圧縮 / 再封緘|
|chunk_size|u32|例: 4096|
|created_at|u64|epoch ms|

※ 内容秘匿なし。改竄検知は署名で行う。

---

## 5. Chunk 設計（最重要）

### 5.1 Chunk 基本構造

`Chunk := {   ChunkHeader,   Payload (ISE済),   Envelope }`

### 5.2 ChunkHeader

|Field|Size|Notes|
|---|---|---|
|file_id|u128|ファイル識別子|
|chunk_index|u32|連番|
|logical_offset|u64|元ファイル位置|
|payload_len|u32|元サイズ|

## 6. ISE 適用仕様（FS用）

### 6.1 使用 ISE モード

|項目|値|
|---|---|
|ISE鍵|8B（Witness互換）|
|ラウンド|8|
|SeqID|Chunk 単位|

## 7. Envelope（FS版）

### 7.1 Envelope 構造（完全一致）

ISE-FS Envelope は **encryptor.Envelope と完全同一**。

|Field|説明|
|---|---|
|KeyVersion|KMS version|
|SeqID|ISEPlan Seq|
|OrderForward|canonical|
|OrderUsedForward|applied|
|Nonce|AES-GCM|
|Ciphertext|gzip+ISE|
|PlainHash|元chunk|
|CipherHash|nonce+cipher|
|CommitSig|真正性|
|OperSig|運用整合|

→ **FS / MQ / Witness 共通**

## 2) Initialチャンク＝強制3N（壊れてはならない）

### 妥当性

これは正しい方向です。あなたのFSは **「インデックスが死ぬと全データが迷子になる」**型なので、Initialの堅牢化は最重要です。ログの流れ（indexが生死を分ける）とも整合します。

ISE-FS LOG 0

### 追加で必要な定義（ここが実装の分岐点）

**Initialチャンクに含めるべき最小集合**を明示する必要があります。現実的には以下です。

- **Superblock（=FS定義）**：magic / version / chunk_size=4096 / feature flags
    
- **Policy root（=冗長性ルール）**：後述の “.gitignore的ルール”
    
- **Key descriptor（鍵そのものではなく参照）**：KeyVersionやKMS locator等（現行EnvelopeのKeyVersion整合）
    
    ISE-code
    
- **Index bootstrap（再生開始点）**：indexログの先頭ポインタ or 世代cursor
    
- **Recovery locator**：修復チャンクの配置制約（別ストレージ等）
    

### 3N の意味（注意点）

- 「3N」は **“3副本” ではなく “3障害ドメイン”**で考えないと破綻します。  
    同一NVMe上に3つ作っても意味がない、という話です。
    
- ここは “強制” にするなら、**置き場所属性**（device class / fault domain）もInitialに含める必要が出ます。

### ただし鍵については整理が必要

現行の封緘は **ISE鍵(8B) + AES鍵(32B) + KeyVersion** という KeyRing/KMSモデル前提です。

ISE-code

  
「鍵も4096世界に統一」は次のどちらかに収束します。

- **A: 鍵“そのもの”はFS外（KMS/TPM）に置き、FS内は参照だけ**
    
    - 整合が取りやすい
        
- **B: 鍵“そのもの”をFS内に4096B KeyChunkとして置く**
    
    - 実装は可能だが、盗難時の意味が変わる（あなたのISE思想上は“守らなくていい”が、運用上は事故る）

## 6) FS目的：データに合わせた冗長性／HW冗長も視野／ランサム不可／論理修復全振り／物理削除はSU以外不可／修復チャンクは別ストレージ限定も可

### 妥当性（狙いは一貫）

これは「ストレージ機能」ではなく「運用ポリシー実装」です。  
あなたのI/Oモデル（write=queue、実書込は非同期）と非常に相性が良い。

### ランサム耐性の“成立条件”

ランサムは大雑把に2種類あります。

1. **暗号化して上書き**
    
2. **削除して脅迫**（スナップショット破壊等）
    

あなたの設計が効くのは主に (2) です。  
(1) に対しては「上書き＝新世代書込」として扱う以上、“暗号化された新データ”自体は書かれてしまいます。  
なのでランサム不可を成立させるには、最低限

- **世代の昇格（active index更新）を誰が許可するか**
    
- **正当な更新とランサム更新をどう分けるか（署名・KAIRO等）**
    

の語彙が必要です。  
ここは ISE の「署名のみが真実」と同型なので、**“適用される世代”は署名で確定**に寄せるのが自然です。

ISE

### 「物理削除はSU以外不可能」の実装解釈

矛盾なく実装する現実解はだいたい3つに分かれます。

- **WORM**：そもそも削除APIを提供しない
    
- **Tombstone**：削除は論理的不可視化（GCは別権限）
    
- **Epoch-GC**：特定epoch以前だけ掃除できる
    

あなたの「論理修復に全振り」と一番相性がいいのは Tombstone/epoch です。  
WORMは強いですが容量破綻しやすい。

### 「修復チャンクを別ストレージ限定」

これは成立しますが、初期定義（Initialチャンク）に

- recovery device locator
    
- recovery allowed policy
    

が入っていないと運用で崩れます。  
（“別ストレージ”が何かが曖昧だと、実装が独自解釈します）

## 1) Initialチャンクの設計：成立するが、署名と冗長前提が未定義

### 1.1 フィールド構成（あなたの案）

### 1.2 ただし「壊れてはならない」に対する最低条件が不足

## 3) 鍵（512-bit）をInitialに入れる：技術的には可能、運用的には危険度が跳ねる

あなたは「鍵も含めて4096B世界で統一」を置いています。  
その結果、「FS作成時に生成した鍵をInitialに格納」が出ています。

ここでの問題は暗号強度ではなく **運用事故**です。

- そのFSが“持ち出しメディア”になった瞬間、鍵が付属している
    
- root/suが読める環境なら鍵も読める
    
- ランサムがroot権限を取った場合、鍵を使って“正当な更新”に見せかけやすくなる
    

あなたのISE思想が「秘匿は目的ではない」でも、  
**ランサム耐性**と両立させるなら「鍵を置くなら、鍵の“使い方”に権限ゲートが必要」です。

つまり「鍵を置く/置かない」ではなく、

- **鍵は置く（統一のため）**
    
- ただし **“冗長領域を書き換える権限”は鍵だけでは足りない**（Owner側の明示署名が要る）

## 5) Dataチャンク：フッタなしは速度面では正しいが、修復思想と衝突します

## 7) ランサム対策（write-queue簡易判定）：方向は正しいが、抜け穴が多いので“守る対象”を明示する必要があります

- 2N/パリティ対象データへの「実ライト」が大量に来たら

### 7.1 これは「防げるもの」と「防げないもの」が分かれます

防げる：

- 突発大量上書きで、冗長まで一気に巻き込むタイプ（多くのランサム）
    

防げない（または誤検知しやすい）：

- **低速・分割**（閾値回避）

### 7.2 だから「守る対象」を定義しないと実装が迷走します

- **Protected Domain**：Initial / Sub / policy / parity / mirror / recovery

- **Normal Domain**：cache / temp / 冗長0  
    → 通常writeでOK
    

あなたが言っている「冗長チャンクへの書き込みは指示必須」は、  
実は「Protected Domainへの更新は署名必須」と同型です。ここまで定義すれば、閾値判定は“補助”に落とせます。

## 1) 4096B − 512bit の件：あなたの違和感は正しいです

まず計算を固定します。

- 4096 **bytes** = 4096B
    
- 512 **bits** = 64B
    
- 4096B − 64B = **4032B**
    

なので「3072+512B」みたいな数字が出てくるのは、どこかで **bit/byte が混ざっている**か、あるいは「サブチャンク参照領域を 3072B に固定」みたいな別ルールが頭の中に存在している状態です。

→ **仕様書では bit 表記を完全排除**して、全部 B/uintXX だけで書き切るのが安全です。

## 2) Initial 3N を同一HWに置く件：成立します（むしろ現実的）

ここ、こちらの前の指摘は「障害ドメイン」という一般論でしたが、あなたの運用要件は

> **Initialは常時3N一致を“運用要件”とする**  
> 一致しないなら、HW異常 or ソフト異常として扱う

なので、**同一HW内の3Nでも意味が成立**します。理由は：

- あなたの目的は「耐災害」ではなく「壊れない／改竄できない」
    
- 初期領域は**比較・多数決・監視**の対象で、RAID的冗長とは別物
    

### あなたの運用フローは仕様として強い

- 初期化：3N完全一致が成立したら初期化完了
    
- アイドル：3Nをコンペア
    
- 不一致発生：
    
    - 対象領域のHWチェック
        
    - 異常なし → 多数決で上書き修復
        
    - 異常あり → SMART系統アラート
        

これは **「正しい1つを選ぶ」ではなく「常時一致させ続ける」**で、設計思想として一段上です。

✅ ここは仕様条文に落とすと強いです。  
（“Initialは単一の真実ではなく、3N一致が真実”）

## 3) Dataフッタ：あなたの判断（付ける）は正解です

- 外部から書き換えられない（=検知＋復旧可能）
    

なら、データチャンクを「フッタ無し」にするメリットは薄いです。

- next pointer の整合性検証

## 4) SubチャンクのTTL＋世代クローン案：筋が良いが、注意点が1つ

あなたの言う

> 上書きTTL → 世代クローン → 親が継承通知 → 旧をクリア

は、実態として **Copy-on-Write + 世代管理 + Reclamation** です。  
「壊れない」「修復できる」FSとしては王道です。

### 注意点（ここを決めないと泥沼化）

「旧をクリア」が意味する操作が、2種類に分かれます。

- **論理クリア**：indexから外す（見えなくする）
    
- **物理クリア**：実領域を再利用（上書き可能化）
    

あなたの「SU以外は物理削除不可」と整合させるなら、

- 旧チャンクは **論理クリアのみ**
    
- 物理再利用は **SU + GCプロセスのみ**  
    に固定すると、思想が崩れません。

## 5) ランサムの書き方パターン：典型は3種、フォルダフラグだけだと抜けます

「よくわからない」は正常です。現場のランサムは、FS視点ではだいたいこれです。

### パターンA：コンテンツ暗号化（上書き型）

- 各ファイルを開いて内容を書き換える（暗号化済みデータを書き戻す）
    
- 拡張子変更、元を削除 など
    

→ 「Protectedフォルダ」フラグで抑止できる部分はありますが、  
**通常フォルダでも大量上書きが発生**するので誤検知/誤停止も起きます。

### パターンB：メタデータ破壊（小さいが致命的）

- データ本体は触らず
    
- **index / next pointer / directory entry** を壊して「見えなくする」
    

→ これは **書き込み量が少ない**ので、あなたの「大量実ライト判定」をすり抜けます。  
フォルダフラグだけでも防げません。  
**Initial/Sub/Index を Protected domain として“署名必須”**にしないと防げません。

### パターンC：世代破壊（復旧ポイント潰し）

- スナップショットやバックアップ、冗長コピーを消す
    
- 復旧不能にして脅迫
    

→ あなたの「冗長領域への書込みに明示指示」を入れるのは、この対策として強いです。

## 6) 「フォルダプロパティにフラグ」は有効。ただし“用途”を限定すると強い

結論として、フォルダフラグは **使えます**。  
ただし、これを「ランサム対策の主軸」にすると抜けます。

一番噛み合う使い方は：

- **Protected flag = 冗長・修復・index関連の更新ポリシーを変えるスイッチ**
    
    - 冗長（mirror/parity）への反映は _明示署名_ がないと進めない
        
    - Sub/Indexの世代更新は _明示署名_ がないと昇格しない
        
    - Dataは書けても、**“確定（commit/epoch昇格）”できない**
        

こうすると、あなたのアイデア（特別キュー/明示指示）と矛盾せずにまとまります。

## 7) ここまでの合意で、仕様が一気に締まります（要点だけ）

あなたの補足を反映すると、ISE-FSのコアはこう固定できます。

1. **Initialは常時3N一致が運用要件**
    
    - init時は完全一致が成立するまで完了しない
        
    - idleで常時比較し、不一致は多数決修復＋HWチェック＋アラート
        
2. **Dataチャンクはフッタを持つ（整合性をチャンク完結）**
    
    - “壊れない”を優先
        
3. **Sub/Indexは CoW + 世代管理 + TTL（論理クリア → SUのみ物理再利用）**
    
4. **ランサム対策は「大量書き込み検知」ではなく「確定権限（commit/epoch昇格）を握る」**
    
    - フォルダフラグはポリシースイッチとして使う

- **Initial 4096B レイアウト（byte offset表）**
    
- **Sub 4096B レイアウト（世代・TTL・親子・署名/CRC含む）**
    
- **Data 4096B レイアウト（ヘッダ＋ペイロード＋フッタ）**
    
- **3N一致監視・多数決修復の状態遷移（擬似コードではなく条文化）**
    
- **Protected flag の意味（commit権限・冗長反映権限）**
    

まで、一気に “詳細設計書の章” として起こせます。

確定権限良いですね。それこそTruncate/Commitの二択で。 で、SU権限で「Cleanup」のようなコマンドで、旧インデックス等の物理クリア、空きスペース確保等を行う。 インデックスチャンクは2N強制にして、基本的にフォルダ構造の破壊を防ぎ、特定フォルダに置いてはそもそもデータチャンクまで2N/パリティを実装して、確定権限を使用しない限り冗長部分への書き込みをする/しない/ライトキュー滞留がN時間を超えたらする、などの細かいカスタマイズ等も。

良い収束です。いまの追加で、ISE-FSの「壊れない／改竄できない」が **FS語彙（truncate/commit/cleanup）**として閉じます。ここからは、多角的に「成立性」「抜け穴」「仕様としての定義単位」を固めます。

---

## 1) Truncate / Commit の二択：設計として強い（ランサム対策の芯）

### 1.1 何が良いか

- ランサムの本質（上書き）を **“書けるが確定できない”**に落とせます。
    
- FSの整合性を「即時整合」ではなく「世代整合」に寄せられます。
    
- “write=queue only” と完全に一致します。
    

### 1.2 用語を固定するとこうなります

- **Truncate**：  
    書き込み結果を _破棄_（＝active indexに昇格させない）  
    既存のactive世代は不変
    
- **Commit**：  
    あるwrite-queue（またはepoch）を _active indexに昇格_  
    ここで初めて「ファイルが更新された」扱いになる
    

この二択を**全ての破壊的操作のゲート**にするのが、あなたの狙いと一致します。

---

## 2) SUの Cleanup コマンド：必須（論理と物理の分離）

あなたが言っているのは正確には

- 通常ユーザ：論理操作（作成・更新予約・commit/truncate）
    
- SU：物理操作（GC / compaction / 旧index破棄 / free space再利用）
    

です。

この分離がある限り、「物理削除はSU以外不可」が自然に実現できます。

### Cleanup の責務（仕様として分けると事故りません）

- **Index GC**：旧世代index/subchunkの物理破棄
    
- **Data GC**：参照されないdata chunkの回収（ただしProtected領域は別扱い可）
    
- **Queue GC**：滞留write-queueの整理（TTL超過など）
    
- **Scrub**：2N/3N比較、パリティ検証、silent corruption検出
    

※ Cleanup は “commit権限”とは別にしておくと強いです。  
（commitは「真実の昇格」、cleanupは「物理衛生」）

---

## 3) インデックスチャンク 2N 強制：成立、ただし “何を2Nにするか” を定義すると盤石

「インデックス」と言っても層が2つあります。

- **Index Log（append-onlyの真実）**
    
- **Index Cache（再構築可能な地図）**
    

あなたの目的（フォルダ構造破壊を防ぐ）からすると、2N強制すべきは **Index Log** 側です。  
Cache側は最悪捨てて再生成できるので、2N強制の価値が薄いです。

### 2Nの運用はこうすると矛盾しません

- Index Log：2N強制、commit対象
    
- Index Cache：冗長0でも可、rebuild対象
    

---

## 4) 特定フォルダで data chunk 2N/パリティ：筋が良い（ポリシー設計に落ちる）

ここは **policy engine** の仕事になります。あなたの「.gitignore的ルール」と同型です。

### 4.1 フォルダ単位で持たせるべきポリシーの最小集合

- `redundancy.data = {0, 2N, parity}`
    
- `redundancy.index = {2N forced}`（ほぼ固定）
    
- `commit_required_for_redundant = true/false`
    
- `queue_policy = {normal, protected, quarantine}`
    
- `queue_ttl_hours = N`
    
- `ttl_action = {auto_redundant_write, auto_truncate, require_commit}`
    

これらは “フラグ”ではなく **決定表**として持たせると、後から増やしても壊れません。

---

## 5) 「確定権限を使わない限り冗長部分へ書かない」：成立。ただし“表層”の扱いに2方式あります

あなたの言葉だと

- 表層（primary）は書ける
    
- 冗長（mirror/parity）は commit されるまで書かない or 別キュー滞留
    

この方針には2つのモードがあります。

### モードA：冗長遅延（deferred redundancy）

- primary は即書く
    
- 冗長は commit で一気に反映
    

**メリット**：commitが強いゲートになる  
**デメリット**：commit前は耐障害性が落ちる

### モードB：冗長隔離（quarantined redundancy）

- primary も “保留領域”に書く（activeにはしない）
    
- commitでactive化し、同時に冗長を生成
    

**メリット**：active側の整合が強い  
**デメリット**：実装と運用が少し重い

あなたの「安全性至上」「壊れない」が最優先なら、思想としては **B がより一貫**します。  
ただし、Linux上のマウントFSとして使う都合で、体験上はAの方が自然です。  
（ここは設計選好ですが、矛盾ではなく“モード選択”です）

---

## 6) 「ライトキュー滞留がN時間を超えたらする」：有効だが、実装上は“自動確定”を避けるのが安全

ここは一見便利ですが、ランサム対策と真正面衝突します。

- 自動で冗長反映＝攻撃者が「待つ」だけで冗長も汚染される
    

なので、TTL超過のアクションは

- 自動commit ❌
    
- 自動冗長反映 △（Protected領域なら危険）
    
- **自動停止／隔離／truncate（または要手動介入）** ✅
    

が安全側です。

あなたの語彙で言うと：

- TTL超過 → **quarantine queueへ移送**
    
- quarantine queueは **SU + 明示commit** が無いと処理しない
    

これなら「運用で詰まる」代わりに「壊れない」が守れます。

---

## 7) この設計が防げる“フォルダ破壊”と“ランサム”の関係整理

あなたがやりたいのは

- フォルダ構造（index）破壊を防ぐ → **index log 2N + commit gate**
    
- データ破壊（暗号化上書き）を防ぐ → **冗長反映をcommit gateの向こうへ**
    
- 復旧ポイント破壊を防ぐ → **cleanupをSU限定・物理削除限定**
    

この3つは互いに補強し合います。矛盾しません。

---

## 8) 仕様としての最小“確定事項”（ここまでの会話の合意を条文化できる形）

- 破壊的更新は **Truncate / Commit** の二択で確定
    
- Commitは **active index昇格**を意味する（＝真実の更新）
    
- Index Log は **2N強制**（フォルダ構造破壊防止の最優先）
    
- 特定フォルダは data も **2N/Parity** を指定可能
    
- 冗長領域の更新は **commitをゲート**にできる（遅延/隔離モード）
    
- 物理削除・空き領域確保は **SUの Cleanup** でのみ実行
    
- TTL超過の自動処理は **quarantine/truncate** を基本（自動commitはしない）
    

---

ここから先は、必要なら一気に **「ポリシー記述（.gitignore風）」の最小文法**まで落とせます。  
例：フォルダごとの `data=parity commit_required=true ttl=72h ttl_action=quarantine` のような。  
あなたの望む「細かいカスタマイズ」は、ここを文法化すれば “仕様” になります。

キャッシュチャンクは想定するに、ファイル名等のデータプロパティとデータチャンク先頭IDの塊でしょうか？ そのあたりは「0N」扱いで、データとしては有るけど、別にSUのCleanupを使わなくても勝手に削除して良いテンポラリみたいな扱いで良いと考えます。 キャッシュのみならず、「作業高速化のために必要だが、保存する意味がない」データは、全て0Nチャンクとしてしまえば、一般権限でも普通に容量確保出来ます。 現状は速さと互換性を求めるなら他にExt4とかNTFSが有るので。

はい、その理解でほぼ正解です。  
むしろ **ISE-FS の思想に最もきれいに合う「キャッシュ／0Nチャンク像」** になっています。以下、設計として整理・検証します。

---

## 1) キャッシュチャンクの正体：あなたの定義で成立します

> ファイル名等のデータプロパティ  
> ＋ データチャンク先頭IDの塊

これは **Index Log ではないが、Index Cache そのもの**です。

役割を明確に言うと：

- **Index Log**
    
    - 真実
        
    - 2N 強制
        
    - Commit対象
        
    - 壊れたら FS が壊れる
        
- **Cache Chunk（Index Cache / Fast Map）**
    
    - 再構築可能
        
    - 0N
        
    - Commit不要
        
    - 消えても問題なし
        

この分離は極めて健全です。

---

## 2) 「0N扱いで勝手に削除してよい」──設計的に完全に正しい

あなたの言う：

> データとしては有るけど  
> SU の Cleanup を使わなくても  
> 勝手に削除して良いテンポラリ

これは、**ISE-FS における「非保護データ領域」**の定義として理想形です。

### 0N チャンクの性質（仕様として書けるレベル）

- 冗長性：0
    
- 参照消失：即破棄可
    
- 一般権限：削除可
    
- Cleanup：不要
    
- Commit：不要
    
- 再生成：可能（Index Log / Data から）
    

つまり **「存在するが、存在を保証しない」** データ。

---

## 3) キャッシュに限らない、0Nチャンクの正しい拡張解釈

あなたが言っているこの部分が重要です：

> 「作業高速化のために必要だが、保存する意味がない」データは  
> 全て 0N チャンクとしてしまえばよい

これは **ISE-FS における新しい“テンポラリ層”の定義**になります。

### 想定される 0N チャンクの例

- Index Cache（path → inode/first chunk）
    
- Directory Listing Cache
    
- Read-ahead Cache
    
- Write Aggregation Buffer（commit前）
    
- アプリ向けワークバッファ（opt-in）
    
- 将来的な Rust OS 用メタキャッシュ
    

これらを **すべて同一の 0N ルールで扱える**のは大きな強みです。

---

## 4) 一般権限で容量確保できる、という点が“決定的に重要”

> 一般権限でも普通に容量確保出来ます

ここが、Ext4 / NTFS と思想的に完全に分岐しているポイントです。

- Ext4 / NTFS  
    → キャッシュと本体が混線しやすい  
    → 削除権限が曖昧  
    → ランサム時に「どこまで壊されたか分からない」
    
- ISE-FS  
    → 0N は **最初から壊れてよい**  
    → 保護対象（Index/Data/Redundant）と完全分離  
    → 一般ユーザが“掃除しても安全”
    

これは **セキュリティ設計としても極めて強い**です。

---

## 5) Commit / Cleanup / 0N の三層分離が、思想的に完結しています

今の会話までを統合すると、ISE-FS の操作権限はこう分かれます。

### 一般ユーザ

- write（queue）
    
- truncate
    
- 0N チャンク削除
    
- キャッシュ再生成
    

### Commit 権限（Owner / 明示署名）

- Index Log の昇格
    
- 冗長反映の確定
    
- 世代更新
    

### SU / Cleanup

- 物理削除
    
- 旧世代回収
    
- 空き領域再利用
    
- Scrub / Repair
    

**0N はこのどれにも属さない**  
→ だから自由に捨てていい。

この三層＋0Nの外部化は、かなり美しい構造です。

---

## 6) 「速さと互換性を求めるなら他にある」──これは設計判断として正しい

> 現状は速さと互換性を求めるなら  
> Ext4 とか NTFS があるので

この割り切りは、ISE-FS を **失敗させないための条件**です。

ISE-FS の価値は：

- 壊れない
    
- 改竄されない
    
- 論理修復できる
    
- ランサム耐性がある
    
- 人間が「削除しても安全」
    

速度・POSIX 完全互換・既存ツール最適化  
→ **やらないほうが正しい**

0N チャンクという逃げ道を最初から用意したことで、  
「遅くてもよいが、詰まらない」FSになります。

- キャッシュチャンクの定義：✅ 妥当
    
- 0N 扱い：✅ むしろ必須
    
- 一般権限で削除可：✅ セキュリティ的に正解
    
- Cleanup 非依存：✅ 運用が詰まらない
    
- 他 FS との差別化：✅ 明確
    

この時点で **ISE-FS は「思想FS」ではなく「用途特化FS」**として完全に立っています。

ここは**分岐点として正しく重要**で、結論から言うと――

## 結論要約

- **インデックスチャンクはフォルダ単位で独立**：✅
    
- 中身は  
    **「データチャンクID列挙 ＋ 子フォルダ（インデックス）チャンクID列挙」**の混合体：✅
    
- フォルダチャンクのプロパティに  
    **`redundancy = {0N,1N,2N,parity}`** を持たせる：✅
    
- **内部的に「正／裏／パリティ」が即判別できるメタ情報を持つ**：✅（必須）
    

---

## なぜ「フォルダ単位インデックス独立」が正解か

### 1. 破壊影響範囲を極小化できる

- 1つの巨大インデックスだと  
    → 1ビット破損＝FS全体に波及
    
- フォルダ単位なら  
    → 破壊はそのフォルダで止まる  
    → **論理修復が局所で完結**
    

これは「壊れないFS」ではなく  
**「壊れても復旧可能なFS」**にするための必須条件です。

---

### 2. 冗長性ポリシーと完全に一致する

あなたが既に持っている前提：

> フォルダごとに  
> 2N／パリティ／1N／0N を指定したい

これ、**インデックスがフォルダ単位で独立していないと成立しません**。

- フォルダA：index 2N
    
- フォルダB：index 0N（キャッシュ的）
    
- フォルダC：index parity
    

→ すべて自然に書けます。

---

### 3. Cleanup / 修復 / 再構築が単純になる

- Cleanup は **「参照されていないフォルダインデックス単位」**で回収可能
    
- 修復は **「このフォルダのインデックスを再構築」**で済む
    
- Rust OS 等で使う場合も、**VFS的に非常に扱いやすい**
    

---

## インデックスチャンクの中身（確定案）

フォルダ単位インデックスチャンクの構造は、あなたの言う通りでOKです。

`[Index Chunk] - Header  - chunk_type = INDEX   - folder_id  - redundancy_mode (0N/1N/2N/parity)   - generation / epoch   - flags (protected / commit_required etc.) - Entry List  - [type, id] の配列    - type = DATA_CHUNK | FOLDER_INDEX     - id   = chunk_id - Footer   - CRC / Hash / Signature`

「データとフォルダが混ざる」こと自体は**問題ではなく、むしろ自然**です。  
UNIXのディレクトリと同じ構造です。

---

## 「正／裏／パリティ」を即判別できるべきか？

### 結論：**YES、必須です**

理由は3つあります。

### 1. 修復・比較処理が高速かつ安全になる

- 2N の場合
    
    - `role = PRIMARY / MIRROR`
        
- parity の場合
    
    - `role = DATA / PARITY`
        

これが**チャンクヘッダだけで判別できる**と：

- 比較
    
- 多数決
    
- 再生成
    
- Scrub
    

が**インデックスを辿らずに**可能になります。

---

### 2. ランサム・誤操作耐性が上がる

- 「これはパリティだから直接書くな」
    
- 「これは裏コピーだから commit 必須」
    

という判断が**チャンク単体で完結**します。  
＝外部からの誤操作が通りにくい。

---

### 3. 将来のHW冗長・別ストレージ対応が楽

すでにあなたは

> 専用ボリュームを含めたHW的冗長も視野

と言っています。

その時、

- 上位4bit：storage class
    
- role：PRIMARY / MIRROR / PARITY
    

がチャンクに埋まっていれば、  
**ストレージ跨ぎの再配置がインデックス非依存で可能**になります。

最低限、各チャンクに以下は持たせた方がよいです。

`- chunk_type - role (primary/mirror/parity/cache) - redundancy_group_id - generation - flags (0N, protected, commit_required etc.)`

- 冗長性制御

- 中身は **データID＋子フォルダIDの混合**で問題なし

符号化方式というか、role on とかのFS管理コマンド整備？ 符号化自体はRustの標準ライブラリで可能でしょうし。 むしろリード/ライトの実IOに関して、中間でISEを噛ませる/噛ませない、 これをInitialチャンク以外の全チャンクに基本的に実装するか（高速ISEだと超低負荷なので、この場合ISEチャンクとして、mkdir時点でこのフォルダチャンク自体はこのISE鍵を使うという情報を、SUのISE鍵で封緘してしまえば、鍵自体がシステムにISEチャンクとして大量に存在するが、どのフォルダでどの鍵を使えば復元できるかどうかがわからない）

了解です。論点は2つですね。

1. **role 等の「符号化」よりも、FS管理コマンド（管理語彙）をどう整備するか**
    
2. **全チャンクに ISE を噛ませるか（常時ISE）／フォルダ単位で鍵を割り当て、鍵情報をSU鍵で封緘する設計が成立するか**
    

結論から言うと、あなたの後段アイデアは **成立します**。ただし「ISEの目的」をファイル秘匿ではなく **“鍵探索（どの鍵で復元すべきか）を困難化する”**側に置いているので、仕様でやるべきことが変わります。

## 1) role の符号化より「管理コマンド整備」が本質：YES

role（primary/mirror/parity/cache）自体は Rust の `u8` + `bitflags` で十分です。問題は「運用語彙」です。

あなたのFSは POSIX互換より **運用安全**なので、管理コマンドは最低でも次が要ります。

### 管理コマンド（最小セット）

- `fsctl status`：Initial 3N一致、index 2N、parity検証、queue滞留状況
    
- `fsctl commit <path|epoch>`：Commit権限で世代昇格
    
- `fsctl truncate <path|epoch>`：保留書込の破棄
    
- `fsctl scrub [--scope <path>]`：2N比較/パリティ検証/修復
    
- `fsctl repair [--scope <path>]`：多数決上書き・再生成
    
- `fsctl cleanup [--scope <path>]`：SU専用の物理回収/空き領域確保
    
- `fsctl policy set <path> ...`：0N/1N/2N/parity・commit_required・ttl_action等
    
- `fsctl key rotate|seal|rekey`：鍵運用（後述）
    

ここまでを語彙として先に固定すると、role/flagsは「実装詳細」に落ちます。

## 2) 「中間でISEを噛ませる／噛ませない」：設計として2モードに分けると崩れません

あなたの要求は「基本は常時ISEに寄せたい」ですが、テンポラリ（0N）などは ISE を噛ませない方が合理的です。

なので仕様を次の2モードに分けるのが自然です。

### モードA：Always-ISE（既定）

- Initial以外の **index/data** は原則 ISE 変換を通す
    
- 目的：**鍵探索困難化**＋改竄検知の統一
    

### モードB：ISE-bypass（0Nのみ）

- 0N テンポラリ・キャッシュは ISE を噛ませない（あるいは簡易署名のみ）
    
- 目的：**一般権限で自由に捨てられる**ことを維持
    

この分離は、あなたの前提（0Nは自由に削除）と衝突しません。

## 3) フォルダ単位鍵割当＋鍵情報をSU鍵で封緘：成立する（ただし“復元可能性”の定義を要固定）

あなたの構想は：

- mkdir時点でフォルダに ISE鍵を割り当て
    
- 「このフォルダはこの鍵を使う」という情報を **SUのISE鍵で封緘**（=KeyMapをISEチャンク化）
    
- 結果として鍵（あるいは鍵参照）がFS内に大量に存在
    
- 外部からは「どのフォルダでどの鍵を使うか」探索が困難
    

これは、「秘匿」ではなく **探索困難性（de-correlation）**を狙っていて、ISEの思想に合っています。

### ただし、ここで固定しないと破綻する定義が1つだけあります

**復元（復旧）とは何か？**  
あなたのISEは「復号」は無いが、mapping log で逆経路を表現する、という立場でしたね。  
同様に、ここでも

- “復元”＝フォルダの鍵を発見して適用できること
    
- “鍵発見”＝SU権限＋KeyMap解封緘が必要
    

と定義しないと、ランサムや誤運用で「鍵はあるのに分からない」事故を起こします。

## 4) この方式の強み：ランサムに対して「暗号化しても確定できない」＋「鍵探索が困難」

あなたの既存の commit gate と合わさると、攻撃者はこうなります。

- データを書ける（queueまではできる）
    
- だが
    
    - 冗長領域への反映は commit 必須
        
    - index昇格も commit 必須
        
- さらに
    
    - どの鍵でどの領域が“正しく”再ISEされるか探索が困難
        

つまり **攻撃成功条件が「SU/commit権限の奪取」に収束**します。  
ここまで落ちれば、対策は権限設計と監査（scrub/alert）に集中できます。

## 5) 逆に弱点：SU鍵が“単一点”になる（ただしあなたの設計なら対処可能）

KeyMapをSU鍵で封緘する以上、SU鍵が重要度MAXになります。

ただしあなたは既に

- Initial 3N一致
    
- scrub
    
- 多数決修復
    
- 物理削除はSUのみ
    

の運用モデルを持っているので、SU鍵についても同じ発想で対処できます。

### 実装上の自然な対処（語彙だけ）

- `fsctl key seal`：SU鍵でKeyMapを封緘
    
- `fsctl key unseal`：Commit権限（Owner署名）＋SU権限の二要素で解封緘
    
- `fsctl key rotate`：KeyMap世代更新（旧世代はCleanupでのみ物理消去）
    

（ここは「提案」ではなく、あなたの運用語彙の延長として自然に必要になるコマンド群です）

## 1) 0N でも ISE を噛ませる：成立します（ただし“0Nの意味”を再定義）

0N の本質は「消えてもよい／確保してよい」でした。  
そこに Always-ISE を被せると、0Nはこう再定義されます。

- **0N = 重要度が低い**ではなく
    
- **0N = 整合性・復元性を要求しないが、改竄検知と探索困難化は適用する**
    

つまり 0N を「テンポラリ」から「**低保証領域（再生成前提）**」に格上げする感じです。  
あなたの“安全性第一”とは矛盾しません。

実装上は、

- 0Nは **Commit不要／削除自由**

## 2) ISEチャンク（KeyMap/鍵情報）を3N：合理的です

KeyMapが最重要メタデータになるので、3Nで守るのは自然です。  
サイズも小さいのでコストは限定的です。

ここで“3N一致運用”を Initial と同様に適用できます。

- idle compare
    
- 不一致 → 多数決復旧＋HWチェック＋アラート
    

これはあなたの運用モデルをそのまま延長できます。

## 3) 「KeyMapはチャンクIDとフェイクISE鍵だけ」：この設計は強い（ただし実装語彙が必要）

あなたのアイデアは要するに：

- FS内には「鍵らしきもの」は大量にある
    
- しかしそれは **フェイク（ダミー）**
    
- “真の復元”に必要なもの（SU鍵）は **外部化**される
    
- だから FS単体では復元不能（≒復号不能ではなく“鍵選択不能”）
    

これは **探索困難化（de-correlation）**としてかなり強いです。

ただし、仕様としては「フェイク鍵」を単なるランダム値にすると、**FS自身も運用不能**になります。  
なので、フェイク鍵は “鍵”ではなく

- `KeyToken`（フォルダ→鍵の対応を解くためのトークン）
    
- `KeySlotID`（外部鍵ストアの参照）
    
- `SealedKeyRef`（SU鍵が無いと復号できない参照）
    

のような **“参照”**に落とす必要があります。

あなたが狙っているのはまさにこれで、言い換えると

> FS内にあるのは「鍵」ではなく「鍵の在り処を示すが、SU鍵無しでは意味を持たない参照」

です。

## 4) 「SU鍵を外部化すれば論理的に復元不可能」：成立。ただし“復元”の定義を固定

ここでいう復元は、あなたのISEの用語に沿うなら

- データの意味復元（復号）ではなく
    
- 正しい変換経路（mapping）や正しい鍵選択を再現できること
    

です。

SU鍵を外部化した状態では、KeyMapが解けず

- どのフォルダがどのKeyTokenに対応するか確定できない
    
- 結果として「正当なcommitチェーン」や「正当な再ISE」ができない
    

→ **運用上の復元が不可能**になります。  
これは設計思想として筋が通っています。

## 5) ただし「オンメモリでSU鍵探索はできない」は安全根拠にしない方がいい

ここだけは釘を刺します。理由は単純で、

という「運用で勝つ」設計に寄せるのが一貫です。

（つまり“探索できないはず”ではなく、“置かない”）

## 6) ここまでを踏まえた最も安全側の整理（仕様に落ちる形）

あなたの方針を仕様語彙にするとこうです。

- **Always-ISE**：Initial以外の全チャンク（0N含む）でISEパイプラインを通す
    
- **KeyMap 3N**：KeyMap/KeyRefチャンクは3N一致運用
    
- **KeyRef only**：FS内に“実鍵”は置かない（置くのはSU鍵無しでは意味を持たない参照）
    
- **SU鍵外部化**：SU鍵は外部（人間入力/物理トークン/別機器）に存在し、FS単体では復元不能
    
- **Commit/cleanup限定**：SU鍵は commit / cleanup / key-rotate など限定操作でのみ必要
    

この形なら、「管理が重い」問題はコマンド整備で吸収でき、セキュリティの根拠は構造になります。

    - SU鍵で封緘されたblob（sealed blob）
        
    - その混合（slot + sealed metadata）
        

ここが決まると、`fsctl key` の語彙と、フォルダ作成（mkdir）の手順が確定します。

## 1) 0N＝ISE対象外 は成立します（むしろ筋が通ります）

あなたの全体方針は

- **守るべきもの**：Initial / Index Log / 冗長データ（2N・パリティ）/ KeyMap
    
- **捨ててよいもの**：キャッシュ・高速化用の一時データ
    

ですから、0Nを

- ISEしない
    
- 署名もしない（または軽いCRCのみ）
    
- 一般権限で削除可
    
- Cleanup不要
    

にするのは、思想と運用に完全整合します。

---

## 2) ただし、0NをISE対象外にするなら「混入防止」の仕様が必須です

0NがISE対象外である以上、攻撃者やバグが

- 本来 2N/パリティ で守るべき領域を
    
- 0N として作らせる／置き換える
    

をやると終わります。

なので、ここは **運用や実装の工夫ではなく“FSのルール”として**固定が必要です。

### 必須ルール（最小）

- **0Nは“データ本体の真実”になれない**  
    → 0Nは _Index Logの参照対象になってはいけない_  
    （参照できるのは「キャッシュとしての補助参照」だけ）
    
- **Commitで昇格できない**  
    → 0Nで書かれたものは active 世代に取り込めない
    
- **0N→1N/2N/Parity への昇格は SU/Commit権限でのみ可能**  
    → 自動昇格禁止
    

この3点を決めれば、「0N bypass」は安全にできます。

## 3) 「SU鍵外部化」「KeyMap 3N」は、0N bypass と両立します

あなたの先の話は「鍵探索困難化」でしたが、これは0Nとは別レイヤなので分離できます。

- KeyMap（鍵参照）は **Index側の保護対象**
    
- 0Nは **性能のための捨てデータ**
    

両者は矛盾しません。むしろ、0NをISE対象外にするほど、KeyMapやIndex Logの保護が重要になります。

## なぜこの方式が最強か（多角的に）

### 1) セキュリティ的に最強

- 0N → 非0N の **状態遷移が存在しない**
    
- 攻撃者は
    
    - 0Nに書く（できる）

**状態機械が一段減る＝攻撃面が消える**

- promote ACL
    
- promote の commit 連携
    
- promote 時の ISE 再処理
    
- promote race condition 対策
    

全部いりません。

代わりに：

- `copy(src_0N → dst_protected)`  
    → **新規作成として扱う**
    

だけ。

FS実装としても、VFS的にも、**一番素直**です。

### 3) ユーザ体験が明快

ユーザに説明するルールがこれだけになります。

- 一時ファイルはどこに作ってもいい
    
- 大事なら **所定の場所にコピー**
    
- それだけで守られる
    

UNIX的にも自然です。

- `/tmp` で作業
    
- `/var/lib/important` にコピーしたら保存
    

ISE-FSはこれを **構造で保証**するだけ。

- 意図せず重要化 → **絶対に起きない**

# ISE-FS Specification

## Draft v0.1

---

## 1. 目的と設計原則

### 1.1 目的

ISE-FS（Indeterminate Signature Encryption File System）は、以下を唯一の目的とする。

- **重要データをロストしない**
    
- **外部からの論理的改竄・ランサムウェアを成立させない**
    
- **破損時に論理修復が可能である**
    
- **行儀の悪いソフトウェアの存在を前提に、安全性を担保する**
    

速度、POSIX完全互換性、既存FSとの性能比較は設計目標に含めない。

---

### 1.2 基本原則

- 最小管理単位は **4096バイト固定チャンク**
    
- **write は即時反映しない**（キューイング）
    
- 真実の確定は **Commit 操作のみ**
    
- **削除は論理と物理を分離**
    
- 安全性を実装・運用・権限モデルの三層で確保する
    

---

## 2. チャンク種別

ISE-FS は以下の4種類のチャンクのみを持つ。

### 2.1 Initial Chunk（初期チャンク）

- FS の存在と所有を定義する最上位チャンク
    
- サイズ：4096B
    
- **3N 強制配置**
    
- 常時 3N 完全一致を運用要件とする
    

#### 主な内容

- FS Owner 情報
    
    - 実名は持たない
        
    - 「外部プログラムに秘密値を入力した結果のシグネチャ」
        
- FS 作成時生成鍵（512bit）
    
- HW 構成情報
    
- 作成時刻／更新時刻
    
- サブチャンク参照（Int64 配列）
    
- フッタ（整合性検証用）
    

#### 運用規則

- 初期化は **3N 完全一致成立時のみ完了**
    
- アイドル時に 3N 比較
    
- 不一致時：
    
    - HW チェック
        
    - 異常なし → 多数決修復
        
    - 異常あり → アラート
        

---

### 2.2 Index Chunk（インデックスチャンク）

- **フォルダ単位で独立**
    
- ディレクトリ構造の真実を保持
    
- **2N 強制**
    

#### 内容

- フォルダメタ情報
    
- エントリ列挙：
    
    - データチャンクID
        
    - 子フォルダ（Index Chunk）ID
        
- フォルダポリシー
    
- 世代情報
    
- 整合性フッタ
    

#### 特徴

- フォルダ単位で破壊影響を局所化
    
- 修復・再構築を局所で完結可能
    
- Commit により世代昇格
    

---

### 2.3 Data Chunk（データチャンク）

- 実データ保持用
    
- フォルダポリシーにより冗長性が決定される
    

#### 内容

- ヘッダ：
    
    - ファイル属性（名前、サイズ、時刻、Owner ID 等）
        
    - 次データチャンクID（EOF=0）
        
- データ本体
    
- フッタ（整合性／改竄検知）
    

---

### 2.4 Temporary Chunk（0Nチャンク）

- **冗長性 0**
    
- **ISE 対象外**
    
- 一時データ・キャッシュ用途
    

#### 特徴

- 一般権限で削除可
    
- Commit 対象外
    
- **非 0N への昇格不可**
    
- Index Log の真実参照対象にならない
    

#### 運用原則

- ルート直下以外で作成可能
    
- 行儀の悪いソフトウェアによる
    
    - 勝手なテンポラリ
        
    - キャッシュ
        
    - 作業ファイル  
        を完全に許容する
        

#### 重要ルール

> **0N チャンクは永久に 0N のままである**  
> 保護したい場合は  
> **非 0N ポリシーフォルダへコピーする**

---

## 3. フォルダポリシー

各フォルダは以下のポリシーを持つ。

- `data_redundancy`：`0N | 1N | 2N | parity`
    
- `index_redundancy`：常に `2N`
    
- `commit_required`：true / false
    
- `ise_enabled`：true / false（0N フォルダのみ false）
    

### ポリシー適用規則

- 新規作成時にのみ適用
    
- 既存データの昇格・降格は存在しない
    

---

## 4. ISE 適用方針

### 4.1 ISE 対象

- Initial Chunk
    
- Index Chunk
    
- 非 0N Data Chunk
    
- KeyMap / KeyRef Chunk
    

### 4.2 ISE 非対象

- 0N Temporary Chunk
    

---

## 5. 鍵管理（KeyMap）

- フォルダ単位で ISE 鍵（KeyRef）を持つ
    
- FS 内には **実鍵を保持しない**
    
- KeyRef は SU 鍵で封緘された参照情報
    
- KeyMap チャンクは **3N**
    

### SU 鍵

- FS 外部に存在
    
- 通常運用時はメモリ常駐しない
    
- Commit / Cleanup / Key 操作時のみ使用
    

---

## 6. 書き込みモデル

### 6.1 Write

- 即時反映せず、write-queue に格納
    

### 6.2 Commit

- 唯一の「真実確定操作」
    
- Index 世代昇格
    
- 冗長領域への反映
    

### 6.3 Truncate

- 保留中 write-queue の破棄
    
- 既存真実は不変
    

---

## 7. Cleanup（SU 専用）

- 物理削除
    
- 旧世代回収
    
- 空き領域確保
    
- Scrub / Repair
    

一般権限からは実行不可。

---

## 8. ランサムウェア耐性

ISE-FS は以下によりランサムを成立させない。

- 書けても Commit できない
    
- 冗長領域は Commit ゲートの向こう
    
- Index は 2N
    
- KeyMap は SU 鍵無しでは解釈不能
    
- 0N は真実になれない
    

---

## 9. 設計上の非目標

- 高速性能
    
- POSIX 完全互換
    
- 既存 FS 置換
    

---

# TUFF-FS

## Write-Queue → Direct I/O 停止条件（確定案）

---

## 0. 大前提（再確認）

- write は **必ず write-queue 経由**
    
- Direct I/O（実ライト）は **特権動作**
    
- 目的は
    
    - ランサムの成立阻止
        
    - 誤動作・暴走ソフトの封じ込め
        
    - HW故障時の二次被害防止
        
- 停止＝**破壊を止めるだけ**  
    （データを消さない／truncateは別）
    

---

## 1. 観測系①：量的異常（Volume / Rate）

### 観測量

- `bytes_written / Δt`
    
- `chunks_written / Δt`
    
- `unique_files_touched / Δt`
    

### 理由

- ランサムは **短時間で大量に触る**
    
- 通常作業（ビルド・コピー）は
    
    - 量は多いが
        
    - ファイル数 or 世代の振る舞いが異なる
        

### 推奨閾値（初期値・保守的）

|指標|閾値|
|---|---|
|bytes/s|**ストレージ理論帯域の 30–40% を 連続 N 秒**|
|chunks/s|**通常平均の 5–10倍**|
|files/s|**1000 files / 10s**（小ファイル大量書換え対策）|

👉 **いずれか超過で「警戒」状態**

---

## 2. 観測系②：構造的異常（Pattern）

### 観測量

- 同一 inode / chunk への **短周期上書き**
    
- 「read → write」を伴わない write
    
- write サイズが **常に固定（暗号ブロック的）**
    

### 理由

- ランサムは
    
    - 読まずに書く
        
    - 一定ブロックサイズで上書き
        
- 正常系は
    
    - read-modify-write
        
    - サイズが揺らぐ
        

### 推奨閾値

- 同一ファイルに  
    **read 無し write が K 回連続**
    
- 書込みサイズが  
    **±5% 以内で M 回連続**
    

（K=3〜5、M=10 程度）

👉 構造異常検出で「警戒」状態

---

## 3. 観測系③：保護領域接触（Critical Touch）

### 観測量

- Index Chunk への write 試行
    
- 冗長チャンク（2N / parity）への write 試行
    
- KeyMap / Initial / Recovery chunk への接触
    

### 理由

- ここは **絶対に無警戒で触らせない**
    
- ランサムも破壊系バグも、最終的にここを触る
    

### 判定

- **commit 権限無しでの write 試行 → 即停止**
    

👉 これは **即 HARD STOP**

---

## 4. 合成判定ロジック（重要）

### 状態遷移を 3 段階にする

`NORMAL   ↓（警戒条件1つ） WARN   ↓（警戒条件が X 秒継続 or 複数同時） FREEZE`

### 各状態の動作

#### NORMAL

- write-queue → Direct I/O 通常動作
    

#### WARN

- write-queue 継続
    
- Direct I/O **スロットリング**
    
- 冗長チャンクへの反映を遅延
    

#### FREEZE（停止）

- write-queue 受付のみ
    
- Direct I/O **全面停止**
    
- truncate / cleanup / commit 以外の実ライト不可
    
- 管理者通知
    

---

## 5. 「停止後に何が出来るか」を明確にする（重要）

FREEZE 状態でも：

- 0N チャンク削除：OK
    
- write-queue の truncate：OK
    
- 読み取り：OK
    
- commit：**SU + 正規鍵があれば可能**
    

👉 **“詰まらない”が“壊れない”**

---

## 6. なぜこの方式が TUFF-FS に合うか

- **単一閾値ではない**  
    → 高負荷作業と攻撃を誤判定しにくい
    
- **Critical Touch を最優先**  
    → Index 破壊は即死なので即止める
    
- **FREEZE は reversible**  
    → 誤検知でも被害ゼロ
    
- **数値は後で調整可能**  
    → 仕様は「構造」、値は「設定」
    

---

## 7. 仕様として固定できる文（そのまま使える）

> TUFF-FS は write-queue を常設し、  
> 量的・構造的・保護領域接触の三系統の観測に基づき  
> Direct I/O の実行可否を制御する。
> 
> 保護領域への無権限アクセスは即時停止とし、  
> その他の異常は段階的にスロットリング・停止を行う。
> 
> 停止はデータ破壊を防ぐためのものであり、  
> 読み取り・truncate・正規 commit を妨げない。

しかし

- 何を見るか
    
- どう合成するか

ここを間違えると、FSが「怖くて使えない」か「止まらない」かになります。

今決めた構造は、  
**TUFF-FS を“実運用に出せる安全FS”にする最小完全形**です。

次に進むなら自然なのは：

結論から言います。  
**その選択肢はアリ**ですし、**TUFF-FSでは“正しい逃がし方”**です。  
ただし、**「無監視」は丸投げではなく“設計上の非監視”として明示的に切り分ける**必要があります。

以下、危険にならない形に整理します。

---

## 1. 「監視しないディレクトリ」は必要か？

### 結論

**必要です。**

理由は単純で、

- 開発環境
    
- ビルドディレクトリ
    
- バイナリ生成物
    
- 一時オブジェクト
    

ここを監視すると、**正常系が常にWARN/FREEZEに引っかかる**からです。  
これはセキュリティ強化ではなく **運用破壊** になります。

---

## 2. ただし「完全無監視」はダメ

やってはいけないのは：

- 監視を切った結果
    
- そのディレクトリ経由で
    
- Index / 保護領域に到達できる
    

これが起きると、**無監視＝裏口**になります。

---

## 3. 正しい設計：監視除外ではなく「監視モード固定」

TUFF-FS では、ディレクトリごとに **Write監視モード** を持たせるのが正解です。

### 3.1 監視モード定義（確定案）

|モード|説明|
|---|---|
|`STRICT`|通常監視（量・構造・Critical Touch 全部）|
|`RELAXED`|量・構造は監視しない、Critical Touchのみ|
|`OFF`|**Direct I/O制御を行わない**（ただし制約あり）|

ポイントは **OFFでもCritical Touchだけは生きる**かどうか、です。

---

## 4. 開発用ディレクトリに適したモード

### 推奨設定

- ビルド／一時ディレクトリ：  
    **`RELAXED`**
    

理由：

- 大量書き込み・固定サイズ書き込み → 無視
    
- しかし
    
    - Index
        
    - 冗長領域
        
    - KeyMap
        
    - Initial  
        への接触は **即停止**
        

👉 これで「うるさくない」かつ「壊れない」

---

## 5. 「OFF」を許してよいケース（限定）

`OFF` を許すのは、以下を **すべて満たす場合のみ**です。

- ディレクトリが **0N専用**
    
- 非0N領域への参照・コピーは **新規作成扱い**
    
- Index Log の真実参照に **絶対に使われない**
    
- 物理的にも別ストレージ or 別クラスが望ましい
    

典型例：

- `/build`
    
- `/tmp`
    
- CI用ワークディレクトリ
    

ここでは

- Direct I/O 停止も
    
- 警戒判定も  
    一切しない
    

→ **壊れてもよい前提**だから成立します。

---

## 6. 仕様としての固定文（そのまま使えます）

> TUFF-FS はディレクトリ単位で Write 監視モードを持つ。
> 
> `STRICT` は全監視を有効とし、  
> `RELAXED` は量的・構造的監視を無効化するが、  
> 重要メタデータへの無権限アクセスは常に停止対象とする。
> 
> `OFF` は 0N 専用ディレクトリにのみ許可され、  
> 当該ディレクトリのデータは TUFF-FS の真実状態に影響しない。

---

## 7. なぜこの設計が一番安全か

- **閾値調整で悩まない**
    
- **開発環境が壊れない**
    
- **セキュリティ境界が構造で守られる**
    
- **誤検知で止まらない**
    
- **裏口を作らない**
    

監視を「切る／切らない」ではなく  
**「どこまで意味を持たせるか」**で分けたのがポイントです。

## 最終評価

あなたの直感は正しくて、

## 結論（仕様として固定）

> **フォルダに `0N` 属性を付与した場合、  
> その配下に作成されるすべてのファイル・サブフォルダは  
> 永続的に 0N として扱われる。**

- 例外なし
    
- 継承は**強制**
    
- 解除は**不可**

## なぜ「明示表記＋強制継承」が最強か

### 1. 昇格・例外・誤解釈が起きない

### 2. 判定が O(1) になる

- パス探索不要
    
- チャンクを見る前に
    
    - 親フォルダ属性を見るだけ
        
- I/O パスが単純・高速・安全
    

### 3. セキュリティ境界が**構造**になる

- 「0N かどうか」は
    
    - ファイルの意思ではない
        
    - アプリの意思でもない
        
    - **フォルダの意思**

### フォルダ（Index Chunk）に持たせる属性

`folder_flags:   - ZERO_N   (this subtree is 0N-only)`

`data_redundancy = 0N ise_enabled     = false monitor_mode   = OFF or RELAXED`

※ 名前は実装依存でOK。**意味だけ固定**します。

- 冗長化（1N/2N/parity）
    
- KeyMap / 保護領域へのリンク
    

> **0N フォルダ配下のデータは  
> TUFF-FS にとって「存在してもしなくても同じ」**

- コピーは **新規作成**
    
- コピー先フォルダのポリシーが適用される
    
- 元データは 0N のまま

---

### 4.1 保全責任者

### 4.2 保管先（既定）

    - 例：環境変数経由での注入も禁止（履歴・プロセス一覧・ダンプ等に残るため）
        

### 4.3 権限制御

- `/root/TUFF.key` のRW権限は **デフォルトでSUのみ**とする
    
- SUが任意に `chmod` 等で権限を緩める行為は可能だが、
    
    - その結果責任は **FS仕様の責任範囲外**とする

## 1. 実行権限モデル

### 1.1 権限区分

|区分|説明|
|---|---|

|Commit-Authorized|SU + 正規MK/KeyFileを保持|

- 4096B 固定論理フォーマット初期化
    
- Initial Chunk（3N）作成
    

#### 実行権限

- **SU のみ**
    

#### 動作

- 対象ブロックデバイスを初期化
    
- セクタ長を **論理 4096B に固定**
    
- Initial Chunk を 3N 配置
    
- Key Fingerprint を生成・表示
    

#### 禁止事項

- 既存 FS 上書きの強制実行

- TUFF-FS パーティションをマウント
    

#### 実行権限

- **SU のみ**

#### 目的

- TUFF-FS パーティションの安全なアンマウント
    

#### 実行権限

- FS 状態の可視化
    

#### 実行権限

- **User / SU**

#### 実行権限

- **SU + 正規 KeyFile 必須**

- 2N / パリティ反映を実行

#### 目的

- 保留 write-queue の破棄
    

#### 実行権限

- **SU**
    

#### 動作

- write-queue を破棄
    
- 現行 active 世代は不変
    

---

### 2.7 `tuffutl cleanup`

#### 目的

- 物理削除・空き領域回収
    
- 旧世代チャンクの回収
    

#### 実行権限

- **SU + 正規 KeyFile 必須**
    

#### 動作

- 旧 Index / Data Chunk の物理削除
    
- 未参照チャンクの回収
    
- 冗長整合性チェック（scrub）

## 3. 0N フォルダ制御（コマンド非介在）

### 原則

- 0N 属性は **フォルダ作成時にのみ決定**
    
- コマンドによる昇格・変更は存在しない
    

### 結果

- `tuffutl` は 0N 制御に **直接関与しない**
    
- コピー操作による新規作成のみが状態遷移手段

### FREEZE 状態

- Direct I/O 停止
    
- 読み取り：可
    
- write-queue 受付：可
    
- commit / truncate / cleanup：可（権限要）

- 明示的なエラーメッセージ出力
    
- 自動修復は行わない
    
- 修復は `cleanup` または再 `commit` に委ねる

- `/root/TUFF.key` の管理責任は **管理者に帰属**
    
- 権限緩和・コピー・外部保存等の結果は **TUFF-FS仕様外**
    
- TUFF-FS は **構造上の安全性のみを保証**

# TUFF-FS

## `rmdir` 仕様（確定）

---

## 1. 基本原則

- `rmdir` は **即時物理削除を行わない操作**として定義する
    
- 削除の可否は **親ディレクトリの冗長性属性**で決まる
    
- 高冗長ディレクトリでは  
    **「削除＝管理判断」** として扱う
    

---

## 2. 親ディレクトリ属性別挙動

### 2.1 親が `0N`

- 挙動：**通常の rmdir と同一**
    
- 即時削除：可
    
- write-queue / commit：不要
    
- Hidden フラグ：使用しない
    

用途：

- `/tmp`
    
- `/build`
    
- キャッシュ
    
- CI ワーク
    

---

### 2.2 親が `1N`

- 挙動：**0Nと同一**
    
- 即時削除：可
    
- commit 不要
    

理由：

#### 挙動

`cp = MV + 冗長性適合`

1. 新規ファイルとして Index エントリを作成
    
2. 所属ディレクトリの冗長性・ISE・監視属性を適用

### 4.2 親ディレクトリが `1N+parity / 2N / 2N+parity`

`file_flags:   - HIDDEN   - DELETE_PENDING`

# TUFF-FS

## `--sync` 動作仕様（確定）

---

## 1. `--sync` の本質的意味

> **`--sync` は「待たない」ための機能であり、  
> 「冗長性を壊す」権限ではない**

したがって：

- **冗長チャンク（2N / parity）への即時書き込みは禁止**
    
- **冗長性の上書き・修正も禁止**
    
- データは **一時的に 1N として確定**
    

---

## 2. 動作モード（明示定義）

### `--sync` 実行時の内部モード

`SYNC_MODE_TEMP_1N`

このモードでは：

- write-queue をバイパス
    
- **Primary Data Chunk のみ Direct I/O**
    
- 冗長チャンクは
    
    - 作らない
        
    - 書き換えない
        
    - 既存冗長を無効化しない（触らない）
        

👉 **「冗長性ペンディングを解消しない」**

---

## 3. 冗長性の扱い（重要）

### `--sync` 実行後の状態

- Index 上は：
    
    - ファイルは「冗長性未適合（PENDING）」状態
        
- Data Chunk：
    
    - Primary のみ最新
        
- 冗長チャンク：
    
    - 前世代のまま or 未生成
        

### 冗長反映タイミング

- **管理者 `commit` 実行時のみ**
    
- または SU が `--sync` を実行した場合のみ例外
    

---

## 4. 権限別の挙動差（ここが肝）

### 4.1 ファイルオーナーの場合

- `--sync` 可
    
- 振る舞い：**TEMP_1N**
    
- 冗長性反映：**不可**
    
- 状態：`REDUNDANCY_PENDING`
    

---

### 4.2 書き込み権限のみ保持（非オーナー）

- `--sync` 可
    
- **必ず TEMP_1N**
    
- 冗長性反映：**不可**
    
- 削除・Hidden 解除：不可
    

👉 書けるが「守る権限」はない

---

### 4.3 SU の場合

- `--sync` 実行時：
    
    - **冗長性反映をスキップ可能**
        
    - つまり：
        
        - TEMP_1N を維持する
            
        - その場で 2N / parity を生成する  
            を選択可能（デフォルトはスキップ）
            

👉 SU は事故を理解した上で選べる

---

## 5. なぜこの設計が正しいか

### セキュリティ

- 一般ユーザが
    
    - 冗長チャンクを壊せない
        
    - ランサム的に全冗長を書き換えられない
        

### 運用

- ビルド成果物などは
    
    - すぐ書ける
        
    - でも「守られたことにはならない」
        

### 実装

- write-queue ロジックを壊さない
    
- 冗長生成は commit に集約
    
- 状態遷移が単純
    

---

## 6. `ls -pend` との連動

`--sync` 後のファイルは：

`fileA [PENDING: redundancy]`

と表示される。

---

## 7. 仕様文（そのまま使える）

> `--sync` は write-queue を経由せず、  
> 対象ファイルを一時的に 1N として Direct I/O に反映する。
> 
> 冗長チャンクの生成・更新は行わず、  
> 冗長性の適合は管理者による commit 操作により初めて確定する。
> 
> 一般ユーザおよびファイルオーナーは  
> 冗長性を即時反映する権限を持たない。

- 権限・鍵・冗長性・削除意味論を **構造で強制**することを目的とする
    

---

## 1. 基本設計原則

- 論理ブロックサイズ：**4096 バイト固定**
    
- すべての構造は 4096B チャンク単位で管理
    
- 冗長性・ISE・監視は **ディレクトリ単位で支配**
    
- 即時破壊操作を排除し、**commit に責任を集約**
    
- 一般ユーザは「速さ」を選べるが「保護」は選べない
    

---

## 2. 権限モデル

|区分|内容|
|---|---|
|User|一般ユーザ|
|Owner|ファイルオーナー|
|SU|ルートファイルシステム管理者|

- 冗長性確定・削除確定は **SU のみ**
    
- 一般ユーザは write / sync のみ可能
    
- 鍵管理は **FS 外責任**
    

---

## 3. 鍵運用仕様

### 3.1 Master Key (MK)

- MK は **tuffutl 内部でのみ使用**
    
- コマンドライン・環境変数での直接指定は禁止
    
- 既定保管先：  
    `/root/TUFF.key`
    

### 3.2 権限制御

- `/root/TUFF.key` は **SU のみ RW**
    
- SU が chmod 等で緩和した場合の責任は仕様外
    

---

**権限**

- SU のみ
    

---

### 4.2 `tuffutl mount` / `tuffutl umount`

**目的**

- TUFF-FS のマウント／安全なアンマウント
    

**権限**

- SU のみ
    

---

**目的**

- FS 状態の可視化
    

**権限**

- User / SU
    

**表示例**

- 冗長性ペンディング数
    
- Hidden / DELETE_PENDING 数

## 5. ディレクトリ操作

### 5.1 `tuffutl mkdir`

`tuffutl mkdir (--0 | --1 | --1p | --2 | --2p) <path>`

- **オプション必須**
    
- 通常 `mkdir` は TUFF-FS 上では拒否
    
- 冗長性・0N属性は作成時に確定
    
- 後から変更不可
    

#### オプション意味

|option|意味|
|---|---|
|--0|0N（テンポラリ専用）|
|--1|1N|
|--1p|1N + パリティ|
|--2|2N|
|--2p|2N + パリティ|

---

### 5.2 `rmdir` 振る舞い（フック）

|親ディレクトリ|動作|
|---|---|
|0N / 1N|即時削除|
|≥1N+P|Hidden + DELETE_PENDING|

ユーザ出力：

`rmdir: delete request queued. waiting for administrator commit.`

## 6. ファイル操作意味論

### 6.1 `cp`

- 同一 TUFF-FS 内：  
    **Index 再所属 + 冗長性適合**
    
- 異なる FS：通常コピー
    
- 実 IO は write-queue に積むのみ
    

---

### 6.2 `mv`

- 同一 TUFF-FS 内：  
    **Index チャンク情報のみ変更**
    
- 異なる FS：cp + rm
    

---

### 6.3 `rm`

|親ディレクトリ|動作|
|---|---|
|0N / 1N|即時削除|
|≥1N+P|Hidden + DELETE_PENDING|

---

## 7. `--sync` オプション

### 7.1 適用範囲

- cp / mv / write 操作
    
- **rm / rmdir には無効**
    

### 7.2 動作定義

- write-queue を経由せず **Direct I/O**
    
- **TEMP_1N モード**で動作
    
- 冗長チャンクは：
    
    - 生成しない
        
    - 書き換えない
        
    - 破壊しない
        

### 7.3 権限別挙動

|実行者|冗長反映|
|---|---|
|Owner|不可|
|Write権限のみ|不可|
|SU|任意（既定：不可）|

冗長性反映は **commit 時のみ確定**

- HIDDEN
    
- DELETE_PENDING
    
- REDUNDANCY_PENDING
    

### 振る舞い

- 読み書き不可

---

## 【全体修正ポリシー】

- **ISE / ISE鍵 / ISEチャンク等の文言は全削除**
    
- 暗号方式は **AES-256（標準HWアクセラレーション前提）に統一**

---

## 1. 暗号仕様（置換）

### 1.1 暗号方式

- TUFF-FS におけるデータ暗号化は **AES-256** を使用する
    
- 暗号モード・IV 生成方式は実装依存とするが、
    
    - 同一鍵・同一チャンクでの IV 再利用は禁止
        
- HW AES 命令（AES-NI 等）の利用を前提とする
    

---

## 3. 鍵運用仕様（拡張）

### 3.3 KeyFile 構造（論理）

`/root/TUFF.key` は以下の論理構造を持つ：

`[Master]   MK_Fingerprint = SHA256(...)  [Keys]   <keyname_1> = SHA256(auto-generated AES key)   <keyname_2> = SHA256(auto-generated AES key)   ...`

- `keyname` は **人間可読な識別子**
    
- 実体鍵は
    
    - 自動生成された乱数
        
    - その **SHA-256 ハッシュのみを保存**
        
- 生鍵は **プロセスメモリ上にのみ存在**
    

---

## 5. ディレクトリ操作（拡張）

### 5.1 `tuffutl mkdir`（更新）

`tuffutl mkdir (--0 | --1 | --1p | --2 | --2p) \               [--keyname <string>] \               <path>`

#### 追加オプション

- `--keyname <string>`
    
    - ディレクトリ専用 AES-256 鍵を指定
        
    - 指定された文字列に対応する鍵を **自動生成**
        
    - 生成した鍵の **SHA-256 を KeyFile に登録**
        

#### 動作仕様

- `--keyname` 指定時：
    
    1. `<string>` が KeyFile 内に **存在しない**ことを確認
        
    2. 新規 AES-256 鍵を生成
        
    3. SHA-256(key) を `/root/TUFF.key` に追記
        
    4. ディレクトリ属性として `KEY_REF=<string>` を設定
        
- `<string>` が既存の場合：
    
    - **エラーを返して異常終了**
        
    - ディレクトリは作成されない
        

#### 制約

- `--keyname` は **mkdir 時のみ指定可能**
    
- 後からの追加・変更は禁止
    
- 省略時は **デフォルト鍵（MK 派生）**を使用
    

---

### 5.2 `rmdir`（更新）

- `rmdir` 自体は鍵操作を行わない
    
- ただし Hidden / DELETE_PENDING 化されたディレクトリは
    
    - **対応する keyname を保持したまま凍結**
        
- 実削除（commit / cleanup）時にのみ、
    
    - 当該 keyname に対応するチャンクを安全に解放
        

---

## 10. commit / cleanup（鍵連動の明確化）

### `tuffutl commit`

- SU + 正規 KeyFile 必須
    
- 以下を同時に処理：
    
    - 冗長性反映
        
    - Hidden 削除確定
        
    - **keyname 参照カウントの更新**
        
- 参照ゼロになった keyname は
    
    - **KeyFile から自動削除しない**
        
    - cleanup 対象とするかは管理者判断

# TUFF-FS 設計書

## Trusted Unified Fault-Tolerant File System

### Design Document – Initial Release

---

## 1. TUFF-FS の目的

TUFF-FS は、次の目的のために設計された **単一ホスト向け・耐破壊ファイルシステム**である。

### 1.1 主目的

- **重要データを誤操作・暴走ソフト・ランサムウェアから守る**
    
- **即時破壊を禁止し、管理判断（commit）に責任を集約する**
    
- **行儀の悪いソフトウェアの存在を前提に、運用を破綻させない**
    
- **高可用性よりも「壊れないこと」「復旧判断ができること」を優先する**
    

### 1.2 非目的（明確に対象外）

- 分散ストレージ
    
- 複数ホスト同期
    
- 高速・低レイテンシ最優先設計
    
- 自動復旧・自律判断
    
- 高度な鍵階層管理・分割管理・復旧鍵
    

これらは **ISE-FS の責務**とし、TUFF-FS には含めない。

---

## 2. 基本設計思想

### 2.1 宣言的ファイルシステム

TUFF-FS では、

- 「どう作るか」
    
- 「どう削除するか」
    
- 「どの冗長性で守るか」
    

を **操作時に明示的に宣言**させる。

曖昧な状態遷移・暗黙の昇格・後付け属性変更は存在しない。

---

### 2.2 フォルダ支配モデル

- **冗長性・暗号・削除ルールはディレクトリが支配**
    
- ファイルは常に「所属ディレクトリの方針」に従う
    
- ファイル単体で冗長性や安全度を変更することはできない
    

---

### 2.3 即時破壊の禁止

- 削除（rm / rmdir）は原則 **即時物理削除しない**
    
- 高冗長ディレクトリでは **Hidden（削除予約）状態**に遷移
    
- 実削除は **管理者 commit / cleanup のみ**
    

---

## 3. 暗号モデル（初回リリース）

### 3.1 暗号方式の前提

> **TUFF-FS におけるすべての実 I/O は  
> AES-256 による暗号化を前提として実行される。**

- データチャンク
    
- 冗長チャンク
    
- インデックスチャンク
    
- メタデータ
    

すべてが **暗号化された状態でディスクに書き込まれる**。

---

### 3.2 鍵モデル（初回リリース）

- 鍵は **Master Key（MK）一本化**
    
- MK は TUFF-FS 外部で管理される
    
- 既定保管先：`/root/TUFF.key`
    
- MK の分割管理・復旧・部分管理は **非対応**
    

※ 高度な鍵階層・復旧モデルは **ISE-FS で実装予定**

---

## 4. 冗長性モデル

TUFF-FS は **論理冗長性**を提供する。

### 4.1 冗長性レベル（ディレクトリ単位）

- `0N`：冗長なし（テンポラリ・ビルド用）
    
- `1N`
    
- `1N + parity`
    
- `2N`
    
- `2N + parity`
    

### 4.2 特徴

- 冗長性は **作成時に確定**
    
- 後からの変更・昇格は存在しない
    
- 冗長チャンクの生成・修復は **commit 時点でのみ確定**
    

---

## 5. 削除モデル（安全設計）

### 5.1 Hidden / DELETE_PENDING

- 高冗長ディレクトリ配下の削除は
    
    - 即時削除せず
        
    - Hidden（不可視）＋ DELETE_PENDING に遷移
        
- 実体は保持される
    

### 5.2 削除確定

- `tuffutl commit`
    
- `tuffutl cleanup`
    

のいずれかでのみ確定

---

## 6. システム構成

TUFF-FS は **2つの主要コンポーネント**から構成される。

---

### 6.1 管理コマンド：`tuffutl`

#### 役割

- 人間起点の制御インタフェース
    
- 構造変更・冗長性確定・削除確定
    
- マウント・初期化・状態確認
    

#### 特徴

- TUFF-FS を操作する **唯一の公式 I/F**
    
- 権限境界・鍵境界を強制
    
- 破壊的操作は commit に集約
    

---

### 6.2 常駐プロセス：`tuffd`

#### 役割

- TUFF-FS の **実行エンジン**
    
- write-queue 管理
    
- オンメモリキャッシュ管理
    
- 低負荷時の実 I/O 実行
    
- 冗長チャンク生成スケジューリング
    
- WARN / FREEZE 状態管理
    
- Initial / Index チャンク整合性監視
    

#### 特徴

- 人間判断を行わない
    
- 自動修復は行わない
    
- 安全側に倒す（FREEZE）
    

---

## 7. I/O 実行モデル

### 7.1 write-queue 前提

- 通常の write は即時ディスク反映しない
    
- write-queue に積まれる
    

### 7.2 commit モデル

- commit により
    
    - write-queue を確定
        
    - 冗長性を反映
        
    - 削除予約を確定
        

### 7.3 `--sync` 例外

- 一般ユーザも使用可能
    
- **一時的に 1N として Direct I/O**
    
- 冗長性は確定しない
    
- 管理者 commit で初めて保護される
    

---

## 8. 運用上の安全境界

- 一般ユーザ：
    
    - 書ける
        
    - 速さを選べる
        
    - 壊せない
        
- 管理者（SU）：
    
    - commit / cleanup が可能
        
    - 責任を持って破壊を確定する
        

---

## 9. まとめ（設計の位置づけ）

TUFF-FS は、

- **事故らない**
    
- **ランサムが成立しない**
    
- **人間の判断を尊重する**
    

ことを最優先にした **運用耐性ファイルシステム**である。

高度な暗号鍵管理・復旧・分割統治は  
**ISE-FS に委譲することで責務を分離**し、  
TUFF-FS は「安全に使える土台」に徹する。

# tuffd 設計（鍵とライトキュー）Draft v0.1

## 1. 前提

- TUFF-FS の全実 I/O は **AES-256** 前提
    
- 通常 write は **write-queue（ライトキュー）**へ積まれ、tuffd が実 I/O を行う
    
- `tuffutl commit` が「真実確定」操作であり、tuffd は人間判断を行わない
    
- 異常終了（プロセスクラッシュ／OSクラッシュ／電断）は必ず起きる前提で設計する
    

---

## 2. 設計目標（鍵とキュー）

### 2.1 守るべきこと

- crash 時に **平文がディスクに残らない**
    
- crash 時に **鍵がディスクに残らない**
    
- crash 時に **キューの再生が可能**（少なくとも「未確定である」ことが分かる）
    
- crash 後に **勝手に確定しない**（commit が無い限り確定しない）
    

### 2.2 捨ててよいもの

- 直前の未確定書き込み（write-queue内）の一部欠落
    
    - ただし「壊れる」ではなく「確定しない」に落とす
        

---

## 3. 鍵の保有方針（結論）

### 結論

> tuffd は **データ暗号の生鍵（AES鍵）を永続化しない**。  
> 鍵は **メモリ上でのみ保持**し、異常終了時は消失させる。

その結果：

- crash 後はライトキューの「未確定分」が残っていても  
    **復号不能＝未確定のまま**になる
    
- 確定は `tuffutl commit` に依存するため、整合性モデルは崩れない
    

---

## 4. ライトキューの永続化モデル（2層）

ライトキューは **2層**で扱う。

### 4.1 RAM Queue（実行キュー）

- 高速
    
- 断電で消える
    
- ここには生鍵を置いてよい（メモリのみ）
    

### 4.2 Disk Journal（キュージャーナル）

- ディスク上に残る「未確定操作ログ」
    
- ただしここには **鍵を含めない**
    
- ここに残るのは **操作の宣言**のみ
    

#### Disk Journal に記録する最低限

- 対象パス（または inode/ID）
    
- 操作種別（write / mv / cp / pending redundancy 等）
    
- 影響範囲（chunk ID群）
    
- 世代番号（index generation）
    
- 追加フラグ（PENDING/DELETE_PENDING 等）
    
- 署名/整合（改竄検出用のMAC相当）
    

※ MAC を「何で」作るかは、ここでは方式を固定しません。  
（鍵を残さないという方針だけ固定）

---

## 5. 異常終了時の扱い（決定ルール）

### 5.1 crash したらどうなるか

- RAM Queue：消失
    
- Disk Journal：残存
    

### 5.2 再起動時の tuffd の動作（自動確定禁止）

- Disk Journal を読み取る
    
- **未確定として復元する**
    
- ただし tuffd は鍵を持たないので、
    
    - 直ちに実 I/O を再開しない
        
    - 状態を **FREEZE** または **PENDING_ONLY** に落とす
        

### 5.3 ユーザ可視の状態

- `ls -pend` で  
    「未確定 write が存在する」ことだけを表示できる
    
- その時点でデータが壊れている扱いにはしない  
    → **未確定が残っているだけ**
    

---

## 6. 再開条件（鍵をどう戻すか）

tuffd は単独で鍵を復帰しない。  
再開は必ず管理者操作とする。

### 再開手順（仕様）

- SU が `tuffutl` を用いて
    
    - KeyFile を用意し
        
    - `tuffutl resume`（または commit/truncate）を実行
        
- これにより tuffd は
    
    - 鍵をメモリへロード（プロセス内）
        
    - Disk Journal を再生可能状態に戻す
        

※ 「resume」という語彙を追加するかは仕様選択だが、意味論はここで固定。

---

## 7. 重要な安全境界（固定）

- **tuffd は crash 後に勝手に進めない**
    
- **commit 無しに確定しない**
    
- **鍵は永続化しない**
    
- **ディスクに残るのは“宣言ログ”のみ**
    

この4点を守る限り、

- 多少の未確定データが失われても
    
- FS が壊れない
    

---

## 8. 実装上の結論（短いまとめ）

- 鍵：RAMのみ
    
- キュー：RAM + Disk Journal
    
- crash：Disk Journal を残して停止
    
- restart：FREEZE/PENDING_ONLY で起動
    
- 復帰：SU が tuffutl で resume/commit/truncate
    

---

ここまでが「鍵とライトキュー」章の骨子です。

この設計の良い点は、**難しい“crash時の中途半端な鍵状態”を設計で消す**ことです。  
「鍵が無ければ進めない」「進めないなら確定しない」――これで TUFF-FS の安全目的に一致します。

次は、この章に続く形で

- tuffd の状態遷移（NORMAL/WARN/FREEZE/PENDING_ONLY）
    
- Disk Journal の最小フィールド定義（鍵なしで改竄検出できる範囲）
    
- `tuffutl` 側の resume / truncate の扱い
    

を設計書に落とせます。

いやライトAPIコールしてキューに投げる時点でAESで良いかと。 問題はRAM上のライトキューが消失することの対策です。 ここはシステムクラッシュと巻き込まれが想定されるので、 キューの長さとRAMの冗長？？

了解しました。整理します。

- **暗号化は「APIでキューに投げる時点でAES」**：賛成です。これで「平文が残る」問題は消えます。
    
- 残る問題は **RAM上のライトキュー消失**（tuffdクラッシュ／OSクラッシュ／電断）で、ここをどう守るか。
    

結論を先に言います。  
**RAM冗長（同一マシン内のメモリ二重化）では解決になりません。**  
落ち方が「プロセスごと／OSごと／電源ごと」なので、冗長RAMも一緒に消えます。  
やるべきは **“キューの永続化の最小単位”を定めて、暗号化済みのキューをディスク（または別デバイス）へジャーナルする**ことです。

あなたの前提（API時点でAES）に合わせて、**最小事故らない設計**を確定します。

# tuffd：ライトキュー消失対策（確定案）

## 1) キューは二段構えにする（RAM + Durable Queue）

### ① RAM Queue（高速・実行用）

- ここは揮発でOK
    
- 失われても「未確定が消えただけ」に落とす
    

### ② Durable Queue（耐障害・再起動用）

- **暗号化済み**キューエントリを追記するだけのログ
    
- tuffdの再起動後に **再生（replay）**できる
    

この②がないと、RAM冗長をどう工夫しても「電断」で終わります。

---

## 2) 「APIでAES」を前提にした Durable Queue の中身

ここは**鍵を永続化しない**で成立します。  
なぜなら、すでに「API時点でAES済み」のため、ディスクに残すのは **暗号文**だけでよいからです。

Durable Queue 1レコード（4096B推奨）の最小フィールド：

- record header
    
    - magic / version
        
    - seq（単調増加）
        
    - op（WRITE / MV / CP / DELETE_REQ など）
        
    - target（inode/ID or path hash）
        
    - payload_len
        
- payload
    
    - **ciphertext bytes**（= APIでAES済みのチャンク列）
        
- trailer
    
    - CRC32C などの破損検出（改竄検出は初回リリースでは不要でも良い）
        

※ ここで言う ciphertext は「データチャンク」だけでなく、必要なら「Index更新差分」も同様に暗号化して入れられます。

---

## 3) いつ Durable Queue に書くか（閾値の話）

「全部ジャーナルすると遅い」問題が出ますが、TUFF-FSは速度二の次です。  
それでも運用上の落としどころとして、**2段階のflushポリシー**にします。

### ポリシー（固定）

- 通常：RAM Queue に積む
    
- ただし以下の条件で **Durable Queue へ同期追記（fsync相当）**
    

#### flush 条件（いずれかで発火）

1. **キュー長**が `N_entries` を超えた
    
2. **キュー滞留時間**が `T_ms` を超えた
    
3. 対象が **≥1N+P のディレクトリ**（重要領域）
    
4. 呼び出し側が `--sync` 相当を指定（＝即時確定したい）
    

この「どの条件で止めるか」ではなく、  
**「どの条件で“永続化を必須にするか”」**で決めるのが正しいです。

---

## 4) Durable Queue の置き場所（巻き込まれ対策）

「システムクラッシュと巻き込まれ」が前提なら、置き場所も切ります。

### 最小構成（同一ディスク内）

- TUFF-FS パーティション内に journal 領域を持つ
    

### 推奨構成（巻き込まれ耐性）

- **別パーティション／別デバイス**に Durable Queue を置く  
    例：OSディスクとは別のSSD、または小型NVMe
    

ここはあなたの「HW冗長も視野」と一致します。

---

## 5) 再起動時の動作（消失しても壊れない）

- RAM Queue：消えている
    
- Durable Queue：残っている
    
- tuffd は起動時に Durable Queue を読み
    
    - 未処理 seq を RAM Queue に復元
        
    - その後、アイドル時に実I/O
        

ここで重要なのは、**commit が無い限り真実化しない**ことは維持します。  
（Durable Queue は「未確定作業の保存」であって、commitではない）

---

## 6) RAM冗長はどう扱うか（結論）

- ECC RAM：有効（ビット反転対策）
    
- しかし「RAM二重化」は効果が薄い（電断で同時消失）
    
- よって、冗長は
    
    - RAMではなく
        
    - **Durable Queue の多重化（2N）**でやる方が筋が良い
        

---

# ここまでの確定（短く）

- API投入時にAESで暗号化：OK
    
- 消失対策は **RAM冗長ではなく Durable Queue（暗号文ジャーナル）**
    
- flush条件は「停止」ではなく「永続化発火」の閾値で決める
    
- 巻き込まれ対策は journal を別デバイスに逃がす

> **Durable Queue（ライトキュージャーナル）および設定ファイルは

## 1. 二重FS構成の位置づけ（明確化）

### 全体構成（推奨）

`/              -> Ext4 (root filesystem)   /etc/tuffd/  -> 設定ファイル   /var/lib/tuffd/       queue/   -> Durable Queue (暗号化済み)       state/   -> 状態ファイル（FREEZE 等）  /mnt/tuff/     -> TUFF-FS (データ専用)`

- **Ext4**：
    
    - OS
        
    - tuffd / tuffutl
        
    - 設定・キュー・状態管理
        
- **TUFF-FS**：
    
    - 守るべきデータのみ
        
    - 自己完結・自己参照を避ける
        

👉  
**TUFF-FS が TUFF-FS 自身の生存を支える構造を持たない**  
＝ 巻き込み設計の完全回避

---

## 2. なぜ TUFF-FS 上に置いてはいけないか

### TUFF-FS 上に Durable Queue を置いた場合の事故

- TUFF-FS が FREEZE
    
- tuffd が回復のために Queue を読みたい
    
- しかし Queue が **FREEZE された FS 上**
    

→ **自己参照デッドロック**

これは設計として致命的です。

---

## 3. root FS（Ext4）に置く利点

### 3.1 障害ドメインの分離

- TUFF-FS の論理破綻
    
- tuffd の再起動
    
- write-queue 再生
    

これらを **Ext4 側から安全に制御**できる。

---

### 3.2 起動順・復旧順が自然

1. root FS マウント
    
2. tuffd 起動
    
3. Durable Queue 読み込み
    
4. TUFF-FS マウント
    
5. 安全に処理再開 or FREEZE
    

👉 init/systemd とも相性が良い。

# tuffd 状態遷移設計

## 前提整理（固定）

- 書き込みは **API時点で AES-256 済み**
    
- tuffd は **write-queue と Durable Queue を管理**
    
- **commit が来ない限り真実化しない**
    
- crash / kill / 電断は常態
    
- tuffd は **自律判断しない**
    

---

## 状態一覧（最小・十分）

`INIT NORMAL WARN FREEZE PENDING_ONLY SHUTDOWN`

---

## 状態定義

### 1. INIT

**起動直後の初期状態**

- Durable Queue の存在確認
    
- 前回異常終了フラグ確認
    
- 未処理キューの有無を検査
    

**遷移条件**

- 未処理キューなし → NORMAL
    
- 未処理キューあり → PENDING_ONLY
    
- 不整合検出 → FREEZE
    

---

### 2. NORMAL

**通常稼働状態**

- RAM Queue 受付：可
    
- Durable Queue 追記：条件付き
    
- 実 I/O 実行：可（アイドル時）
    
- 読み取り：常時可
    

**遷移条件**

- キュー滞留超過 → WARN
    
- 内部異常（I/O失敗等） → FREEZE
    
- SIGTERM → SHUTDOWN
    

---

### 3. WARN

**警告状態（継続可能）**

- RAM Queue 受付：可
    
- Durable Queue 追記：**強制**
    
- 実 I/O 実行：可（低速）
    
- 読み取り：可
    

**典型トリガ**

- RAMキュー長 > 閾値
    
- RAM滞留時間 > 閾値
    
- Durable Queue サイズ逼迫
    

**遷移条件**

- 状況改善 → NORMAL
    
- 悪化 → FREEZE
    
- SIGTERM → SHUTDOWN
    

---

### 4. FREEZE

**安全停止状態**

- RAM Queue 受付：**不可**
    
- Durable Queue 追記：**不可**
    
- 実 I/O 実行：不可
    
- 読み取り：可
    
- 状態通知のみ
    

**意味**

- 「これ以上進めると壊れる」
    

**解除条件**

- SU による `tuffutl commit`
    
- SU による `tuffutl truncate`
    
- SU による `tuffutl resume`
    

※ tuffd 自身は解除しない

---

### 5. PENDING_ONLY

**未確定キュー保持状態**

- RAM Queue 受付：不可
    
- Durable Queue 読み取り：可
    
- 実 I/O 実行：不可
    
- 読み取り：可
    

**典型トリガ**

- crash 後再起動
    
- Durable Queue に未処理エントリあり
    

**遷移条件**

- SU `commit` → NORMAL
    
- SU `truncate` → NORMAL
    
- SU 明示指示なし → 継続
    

---

### 6. SHUTDOWN

**正常終了状態**

- RAM Queue flush（Durable Queueへ）
    
- 実 I/O 停止
    
- 状態保存
    

---

## 状態遷移図（ASCII）

          `+------+           | INIT |           +--+---+              |      +-------+--------+      |                |   no pending       pending      |                |      v                v  +--------+      +--------------+  | NORMAL |<---->| PENDING_ONLY |  +---+----+      +------+-------+      |                    |      | warn                | SU commit/truncate      v                    v   +------+           +--------+   | WARN |---------->| NORMAL |   +--+---+           +--------+      |      | fatal / unsafe      v  +--------+  | FREEZE |  +---+----+      |      | SU commit / truncate / resume      v  +--------+  | NORMAL |  +--------+`

---

## 設計上の重要ポイント（固定）

### 1. 自動復帰は存在しない

- FREEZE
    
- PENDING_ONLY

---

### 2. 状態は「安全側」にしか遷移しない

---

### 3. crash 後の意味論

- データは壊れていない
    
- ただし **未確定**
    
- 状態として PENDING_ONLY に落とす
    

---

## 実装チェックリスト（そのまま使える）

-  起動時に INIT → 判定
    
-  状態は単一 enum
    
-  状態遷移は1箇所で集中管理
    
-  FREEZE/PENDING_ONLY では I/O 実行禁止
    
-  commit/truncate/resume 以外で解除不可

## 1️⃣ 「HBM4はDDR5主軸か？」という問いの評価

### → **Yes（生産・経営の実態として）**

あなたの問いは

> *「HBM4がDDR5“規格”か？」ではなく  
> 「**DDR5世代の汎用量産ラインを主軸にしないと、HBM4投資は成立しないのでは？**」

という意味ですが、**これは完全に正鵠**です。

### 現実の構造

- **HBM4専用ライン100%**  
    → 電力・DC破綻・需要変動時に即「死に金」
    
- **DDR5世代プロセス主軸 + HBM派生**  
    → 唯一、減価償却と需給変動を耐えられる
    

SK hynix / Samsung / Micron すべて、

- 前工程：**DDR5世代（1b/1c nm）と装置・人材を共有**
    
- 後工程：**HBM専用（積層・TSV・Hybrid bonding）**
    

という **「二毛作」構造** を取らざるを得ません。

## 2️⃣ 「HBM4は技術的に完了しているか？」

### → **No。真っ只中。むしろ詰まり始めている**

あなたが列挙した3点は、すべて **未解決コア問題** です。

### (1) 微細DDR5セル × 多層積層＝歩留まり地獄

- 16Hi + 1c nm + Hybrid bonding
    
- → **量産安定域に未到達**
    
- 歩留まりがHBM価格の8割を決めている
    

### (2) 2048bit I/Oを「使い切れる側」がいない

- GPU/TPU側が
    
    - ダイ肥大
        
    - 消費電力増
        
    - CoWoSキャパ依存  
        に引きずられる
        
- **帯域はあっても“流し切れない”**
    

### (3) 排熱・冷却がDC制約と正面衝突

- HBM4自体より

## UEFI における NVRAM 容量の規定（事実）

### ■ 規格上の下限

UEFI仕様では、NVRAM（Variable Storage）について **厳密な総容量の下限は規定していません**。

- **総容量：64KB〜128KB 程度**

- **実質使用可能：20〜50KB前後**
    
- Secure Boot 有効時はさらに圧迫
    

というのが **ほぼ全ベンダ共通の現実**です。

- ユーザー操作で消える

## 1) MKはどこに置くべきか（最小・現実解）

### 結論

**MK実体は NVRAM ではなく TRON-STATE パーティションへ**。  
ただし **平文は不可**なので、MKは必ず「包んで」保存します。

### 方式（おすすめ順）

#### A. ユーザ秘密（PIN/パスフレーズ/キーファイル）でラップ（TPM不要）

- MKは **KEK（Key Encryption Key）** で暗号化して保存
    
- KEKは「ユーザが持つもの」からKDFで生成
    
- TRONは「復号に必要な素材」をOSに渡さない（ここが強い）
    

**TRON-STATEに保存するもの（例）**

- `mk_wrapped`（AES-KW/GCM等でラップしたMK）
    
- `kdf_params`（salt/iter等）
    
- `key_id`（UUID）
    
- `mk_hash`（確認用、SHA-256で十分）
    

**UEFI NVRAMに保存するもの（例）**

- `key_id`（UUID、16B〜）
    
- `boot_flags`（数バイト）
    

これならNVRAMは“ポインタ”で済みます。

#### B. TPMシール（使うなら「オプション」にする）

あなたの懸念（TPM鍵の特定・実装依存）を踏まえると、  
**TPMは「あるなら使える」程度の位置づけが妥当**です。

- TPMが使える環境：MKをTPMシールし、TRON-STATEには“参照”だけ
    
- 使えない環境：A方式にフォールバック
    

👉 つまり **「TPMは加点、非TPMが標準」**にしておくと安全です。
