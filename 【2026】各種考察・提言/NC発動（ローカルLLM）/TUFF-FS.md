## 仕組みの最小形（公開不要の範囲で）

### 1) バイナリ・マニフェスト（実行ホワイトリスト）

- `exe/dll` を含む配布物を **丸ごとハッシュ木**（ファイル単位＋全体）
    
- それに対して **ISEシグネチャ**を付与
    
- その結果を **witnessログ**に封印（時刻＋発行主体＋用途タグ）
    

### 2) 実行ゲート（Windows外の判断）

- 実行前に必ず
    
    - パッケージ全体の整合
        
    - 個別ファイルの整合
        
    - 依存DLLの整合  
        をチェック
        
- **一致しなければ実行しない**（ログだけ残す）
    

### 3) 「更新」は“差分署名”で管理

- 旧マニフェストと新マニフェストを両方残す
    
- 更新は「上書き」ではなく、**新しいwitnessの追加**だけ
    

これで、DLLサイドロード系は「成立しても実行前に落ちる」側に寄せられます。  
（Windowsのロード順序を直すのではなく、**実行の入口で止める**。）

## 3. 致命的に重要な補強点（ここ外すと破綻）

### ①「実行単位」は EXE ではなく **Execution Set**

DLL単体検証では足りません。

**必須**：

- EXE + 同一ディレクトリ内DLL
    
- 依存DLLの**ハッシュ集合**
    

`execution_set_hash = hash(   exe_hash ||   dll1_hash ||   dll2_hash ||   ... )`

→ manifest は **集合ハッシュ**を持つべき。

## ①「使用DLL含め全実行ファイルに強制」

→ **正解。ただし“単位”を明確化が必要**

### 実行単位の定義（標準文言レベル）

**Executable Unit（EU）** を次の集合として定義すべきです。

- 主実行ファイル（EXE / ELF 等）
    
- 実行時に同一ディレクトリまたはRPATHからロードされるDLL / SO
    
- 遅延ロードDLLも含む
    

#### FS側で必要なこと

- 初回実行時に
    
    - 実際にロードされたDLL一覧を捕捉
        
    - **EUハッシュ集合を確定**
        
- 以後
    
    - EU構成に変更があれば **即 invalid**
        

👉 これにより  
**DLL side-loading = EU破壊 = 実行不可**  
になります。

## ② ファイルinfoに「SU」追加（true = W禁止）

これは非常に良い。  
**SU = Secure Unit / System Unit** として定義できます。

### SU=true の意味（標準定義案）

- TUFF-FS上で：
    
    - `write()` / `truncate()` / `rename()` / `unlink()` **禁止**
        
    - mmap write も禁止
        
- 属性変更も禁止（chattr相当）
    

### 実行時ルール

- SU=true の EU は：
    
    - 構成ファイルの **1バイトでも変化 → 実行拒否**
        
- SU=false の場合：
    
    - EU再確定は許可（開発用途）
        

👉 **SUは暗号ではなく「状態」**  
→ 標準化しやすい／輸出規制にも触れにくい。
