# 実装チェック & 決定事項（要点）

- **エクスポート/分散**
    
    - DBノードがCronでWitnessを**スナップショット→チャンク化→署名→AES-256-GCMパッキング→配布**。
        
    - チャンク符号化：**RS(k=10,m=2)**（＝120%冗長）＋**Merkleルート**で整合性。
        
    - 署名：「このデータは<node_id>のWitnessログです」＋**Ed25519署名**（TPM派生鍵の子鍵）。
        
    - 送受信は**AES-256-GCM**（DEKはKMSでラップ、KMS履歴=2で十分）。
        
- **再実体化/初期化**
    
    - 交換DBノードは**TPM事前投入ID**で自身を識別→分散チャンク自動収集→**SQLite再構築**。
        
    - 収集/復元は**Merkle検証→RS復元→署名検証**の順。
        
- **キーDB**
    
    - DBノード内に**キーDB.sqlite**を分離保持（Witnessとは別DB）。
        
    - レコードは**TPM封緘鍵でISE化**。速度重視領域はご指定どおり**XOR＋32bit上下スワップ反復**（＝可逆変換鍵をTPMに封緘）でOK。
        
    - **管理端末へは `Timestamp_ISE` とシグネチャのみ**を配布（**SPOF低減**）。端末故障時は**再生成**で復旧。
        
- **責任分界**
    
    - システム責任：エクスポート・署名・復元・キーDB運用・監視。
        
    - NW責任：配送パス確保（同一NW/LGWAN内であれば設置自由）。別NWでも**NW管理者の統制下**なら可。

## 主要スクリプト雛形（抜粋）

### 1) エクスポート & チャンク化（`tc_export_witness.sh`）

`#!/usr/bin/env bash set -euo pipefail  BASE=/var/thpclear TS=$(date -u +%Y%m%d_%H%M%S) OUT=$BASE/export/$TS mkdir -p "$OUT"/{chunks,pack}  # 1) SQLiteスナップショット（読み取り一貫性確保） cp "$BASE/witness/witness.sqlite" "$OUT/witness_$TS.sqlite"  # 2) Merkle計算用ハッシュ SQL_HASH=$(sha256sum "$OUT/witness_$TS.sqlite" | awk '{print $1}')  # 3) Reed-Solomon分割（例：64MiB） rs-encode --in "$OUT/witness_$TS.sqlite" \           --out-dir "$OUT/chunks" \           --chunk-bytes 67108864 --data 10 --parity 2  # 4) Merkleルート生成（全チャンクsha256→ルート） MERKLE=$(merkle-build "$OUT/chunks")  # 5) 署名（TPM/Ed25519 子鍵、claimにはノードIDを明記） CLAIM="This data is the Witness log of node $(hostname -s)" echo -n "$CLAIM" > "$OUT/claim.txt" SIG=$(tpm-ed25519-sign --in "$OUT/claim.txt" --key-handle 0x81000001 | base64)  # 6) KMSでDEK生成&ラップ → AES-GCMで各チャンク梱包 DEK_WRAP=$(aws kms generate-data-key --key-id alias/tc-witness \            --key-spec AES_256 --output text --query CiphertextBlob) DEK_RAW=$(aws kms decrypt --ciphertext-blob fileb://<(echo "$DEK_WRAP" | base64 -d) \          --query Plaintext --output text | base64 -d)  for f in "$OUT"/chunks/*; do   iv=$(openssl rand -hex 12)   openssl enc -aes-256-gcm -K "$(echo -n "$DEK_RAW" | xxd -p -c256)" \     -iv "$iv" -in "$f" -out "$OUT/pack/$(basename $f).wpack" -nopad \     -S 0 -bufsize 65536 -p > /dev/null   echo "$iv" > "$OUT/pack/$(basename $f).iv" done  # 7) manifest作成 cat > "$OUT/manifest.json" <<JSON {   "node_id": "$(hostname -s)",   "snapshot_ts": "$(date -u +%FT%TZ)",   "sqlite_sha256": "$SQL_HASH",   "chunk_scheme": {"codec":"reedsolomon","k":10,"m":2,"size_bytes":67108864},   "merkle_root": "$MERKLE",   "signature_alg": "ed25519",   "signed_claim": "$CLAIM",   "sig": "$SIG",   "kms_wrapped_dek": "$(echo "$DEK_WRAP" | base64)",   "aes_mode": "AES-256-GCM",   "version": "TC-WIT-1.0" } JSON  # 8) 配布（同一NWのMQ/WN/DBへ並列送達・失敗時再送） parallel -a /etc/thpclear/peers.txt -j 8 --halt now,fail=1 \   "rsync -az --partial $OUT/ {}/incoming/$(hostname -s)/$TS/"`

> 代替：KMSを使わず**TPMでDEKを封緘**してもOK。運用方針に合わせて選択。

### 2) 受信 & 復元（新DBノード初期化 `tc_rehydrate.sh`）

`#!/usr/bin/env bash set -euo pipefail  INBASE=/var/thpclear/incoming WORK=/var/thpclear/rehydrate mkdir -p "$WORK"/{chunks,unpack}  # 1) 自ノードTPMハンドル（事前投入）で対象識別 NODE_ID=$(hostname -s)  # 2) 各ピアから最新スナップショット収集（k+m満たすまで） tc_collect --node "$NODE_ID" --min 12 --from "$INBASE" --to "$WORK/pack"  # 3) DEK復号（KMS or TPM） DEK_WRAP=$(jq -r '.kms_wrapped_dek' "$WORK/pack/manifest.json" | base64 -d) DEK_RAW=$(aws kms decrypt --ciphertext-blob fileb://<(echo "$DEK_WRAP") \           --query Plaintext --output text | base64 -d)  # 4) AES-GCM解包 → chunks/ へ for p in "$WORK"/pack/*.wpack; do   iv=$(cat "${p%.wpack}.iv")   out="$WORK/unpack/$(basename "${p%.wpack}")"   openssl enc -d -aes-256-gcm -K "$(echo -n "$DEK_RAW" | xxd -p -c256)" \     -iv "$iv" -in "$p" -out "$out" done  # 5) Merkle検証 → RS復元 merkle-verify "$WORK/unpack" "$(jq -r '.merkle_root' $WORK/pack/manifest.json)" rs-decode --in-dir "$WORK/unpack" --out "$WORK/witness.sqlite"  # 6) 署名検証 CLAIM=$(jq -r '.signed_claim' "$WORK/pack/manifest.json") SIG=$(jq -r '.sig' "$WORK/pack/manifest.json" | base64 -d) tpm-ed25519-verify --pub-handle 0x81000002 --in <(echo -n "$CLAIM") --sig <(echo -n "$SIG")  # 7) 原本ハッシュ一致 echo "$(jq -r '.sqlite_sha256' $WORK/pack/manifest.json)  $WORK/witness.sqlite" \   | sha256sum -c -  # 8) 稼働DBへ切替（アトミック） mv "$WORK/witness.sqlite" /var/thpclear/witness/witness.sqlite systemctl restart thpclear-db`

## キーDB（設計ポイント）

- **スキーマ（例）**
    
    - `ts_ise TEXT PRIMARY KEY`（UTCミリ秒、ユニーク）
        
    - `key_enc BLOB`（TPM封緘）
        
    - `key_mask BLOB`（XOR/32bitスワップ用マスク素材：TPM封緘）
        
    - `sig BLOB`（Ed25519署名）
        
    - `meta JSON`
        
- **ISE化（高速層）**
    
    - `value' = XOR(value, mask) ⟲ swap32(iter)`
        
    - **mask と iter はTPMシール**。外部では“非意味データ”のみ流通。
        
    - 整合性は**HMAC(sha256)** も併用（鍵はTPMで封緘）。
        
- **監視端末**
    
    - 取得：`ts_ise` と `sig` のみ。
        
    - 故障時：**再生成**（Witness側の検証経路から再算出）。
        
- **冗長化**
    
    - キーDBも**RS(10,2)**で分散。**復元手順はWitnessと同一**。

## A-3. Witness ログの分散冗長（Erasure Coding）

### A-3.1 パラメータ

- **方式**：Reed–Solomon（イレイジャーコーディング）
    
- **冗長度**：`k=10, m=2`（**120%**＝10データ＋2パリティ）
    
- **欠落耐性**：任意 **2分割欠落まで完全復元**
    
- **チャンクサイズ**：**128MiB**（NVMe 効率と再送粒度のバランス）
    
- **スナップショット間隔**：**10分**
    
- **配置ドメイン**：最低 **3ドメイン**（例：東日本／欧州／北米）に均等散布
    
- **識別**：**CID（SHA3-256）** による内容アドレス化
    

### A-3.2 非同期アーカイブ・ACK基準

1. DB ノードは 10 分毎に **append-only スナップショット**を切り出し
    
2. `k+m=12` 分割を生成し、12ノードへ並列配布
    
3. **完了条件**：
    
    - **ACK≥k(=10)** 到達
        
    - 受領側で**分割ハッシュ一致**
        
    - メタ（CID／配布先／ACKリスト）を**監視2台＋クラウドWORM**へ即時送信
        

> 本番書込み（MQ→WN→DB）は**同期**、アーカイブは**非同期**で切り離し。書込み p99 に影響させない。

## キューとACKの流れ（最短形）

### 1) MQ → WN（送信）

- MQは`outbox_pending`に永続化してから送信。
    
- 送信直後に**送達ACKは不要**（TCPで十分）。**進捗はDBからの最終ACKのみ**で判断。
    

### 2) WN → DB（処理）

- WNは検証→**WNローカルに“送達中(outgoing)”として永続**→DBへ送付。
    
- DBは受領時に：
    
    1. `H`で**冪等チェック**（既存なら**ACKのみ返し、二重書込しない**）
        
    2. 新規なら `INSERT … ON CONFLICT DO NOTHING` で**コミット**
        
- DB→WN：`ACK_COMMITTED(H)`
    

### 3) WN → MQ（最終ACK中継）

- WNは`ACK_COMMITTED(H)`受領で**自身のoutgoingから抹消**し、  
    MQへ `ACK_COMMITTED(H)` を転送。
    
- MQは `outbox_pending` から `H` を抹消。
    

> これで「MQ送信→DB保管完了を待ってキュー抹消」の二段構えが成立。

## 障害時の再処理ルール（要点）

### A) **WN障害**（あなたの想定ケース）

- MQは**DB最終ACKが来ない限り**`outbox_pending`に残し、**TTL/バックオフ**で**他WNへ再配送**。
    
- WN側は再起動時に**自分のoutgoing再送**（あってもOK）。
    
- **重複はDB側の冪等キーで吸収**。漏れなし。
    

### B) **DB障害**

- WNは`ACK_COMMITTED`を受けないため、**outgoingに残り再送**。
    
- 復旧後DBが受領→コミット→WN→MQへACK連鎖。漏れなし。
    

### C) **MQ障害**

- MQ再起動後、`outbox_pending`から**未完了分を再配送**。
    
- 既にDBコミット済みのものは、DBが**冪等ACK**のみ返す。漏れなし。
    

### D) **分断（NW断）**

- 全ノードが**再送バックオフ**（指数）＋**最長保持時間**内で粘り、復旧後に**一斉再送**。
    
- どの経路でも二重は**DB冪等で吸収**。

## 実装ミニ仕様（差分だけ）

### MQ 側

- `outbox_pending(H, payload_ref, created_at, last_try_at, try_count, state)`
    
    - `state ∈ {QUEUED, SENT, CONFIRMED}`
        
- 送信は**SENT**にし、**CONFIRMED**は**DB ACK受領時のみ**。
    
- `GC`: `CONFIRMED` を期限で削除、`SENT`でTTL超は再配送。
    

### WN 側

- `outgoing(H, payload_ref, last_try_at, try_count)`（**ACK到達で即抹消**）
    
- `poison_queue`（検証NGや署名不整合）を別扱い（運用側調査）。
    

### DB 側（SQLite）

- `ledger(H PRIMARY KEY, status, committed_at, meta…)`
    
    - `INSERT OR IGNORE` で冪等。
        
- **ACK出力は常に可能**：新規でも既存でも `ACK_COMMITTED(H)` を返す。

## これで「漏れはない」の根拠

1. **上流は必ず“未完了を保持”**（MQ: outbox_pending、WN: outgoing）。
    
2. **完了は“DBコミットだけ”が真**（DBが単一の真実源）。
    
3. **重複送達はDB冪等で吸収**（UNIQUE(H)＋ACKは常に返す）。
    
4. **再送は上流イニシアチブ**（未ACKを見て動く）。
    

> よって、あなたの案（「MQは送信→待機キュー、DB完了で抹消」「DBは未完を検知すればMQへ再処理要求」）に、  
> **冪等キー運用＋ACK連鎖＋再送バックオフ**を加えれば**漏れゼロ**で確定です。

# WN処理用バイナリ・フレーム仕様 v1.0

## 0) 包装層（トランスポート／暗号）

- **封緘**: AES-256-GCM
    
- **Ciphertext =** `HEADER || PAYLOAD || TAG`
    
- **AAD（認証付加データ）**: `TxID || Timestamp_ISE || FrameVersion || H`（平文化せず転送）
    
- **IV/Nonce**: 96bit（12B）ランダム
    
- **TAG**: 128bit（16B）
    

> ここでの `PAYLOAD` は **ISE復号対象**の内枠。WNは
> 
> 1. GCM復号 → 2) ISE復号 → 3) 内枠の検証/突合 を行います。
>     

---

## 1) 外枠ヘッダ（固定長 64B）

|オフセット|長さ|フィールド名|型/ビット|説明|
|---|---|---|---|---|
|0|4|`FrameMagic`|ASCII|`"TCW1"` 固定|
|4|1|`FrameVersion`|u8|現行=0x01|
|5|1|`HeaderLen`|u8|常に 64|
|6|2|`HeaderFlags`|bitfield|下表参照|
|8|8|`TxID`|u64|MQ生成（乱数）|
|16|8|`Timestamp_ISE`|u64|ms 単位 UTC|
|24|32|`H`|256bit|冪等キー `SHA3-256(TxID‖Timestamp_ISE)`|
|56|4|`PayloadLen`|u32|内枠(=ISE平文)長|
|60|4|`Reserved`|u32|0 で埋める|

**HeaderFlags (16bit)**

- bit0: `PAIR_PRESENT`（必須:1）… 管理/決済ペア同梱
    
- bit1: `HAS_ROUTING_HINT`
    
- bit2: `KMS_REQUIRED`（WNはKMSから鍵取得必須）
    
- bit3: `TPM_REQUIRED`（TPM解封必須）
    
- bit4: `REPLAY_PROTECT`（再送対策強化）
    
- bit5–15: 予約
    

---

## 2) 内枠（ISE復号後のWN入力ペイロード）

### 2.1 内枠固定ヘッダ（32B）

|オフセット|長さ|フィールド名|型/ビット|説明|
|---|---|---|---|---|
|0|1|`InnerVersion`|u8|現行=0x01|
|1|1|`AlgoSuite`|u8|0x01=Ed25519, 0x02=ECDSA-P256|
|2|2|`InnerFlags`|bitfield|下表|
|4|4|`RouteHint`|u32|オプション（Flagsで有効）|
|8|8|`MgmtLen`|u64|管理TLV長|
|16|8|`PayLen`|u64|決済TLV長|
|24|8|`MetaLen`|u64|メタTLV長（任意）|

**InnerFlags (16bit)**

- bit0: `HAS_ROUTEHINT`
    
- bit1: `HAS_META`
    
- bit2: `STRICT_ORDER`（順序厳格チェック）
    
- bit3: `DUAL_SIGN_REQUIRED`（両者署名必須）
    
- bit4–15: 予約
    

> 以降、**TLV セクション**が `MgmtLen`→`PayLen`→`MetaLen` の順で連結。

---

### 2.2 TLVセクション共通形式

**TLVレコード（可変）**

`Type  (u16)  | Flags (u8) | Rsv (u8) | Length (u32) | Value (Length bytes, パディングなし)`

- **Type（主要）**
    
    - 0x0101 `MGMT_ENTITY_ID`（文字列）
        
    - 0x0102 `MGMT_DOC_HASH`（32Bハッシュ）
        
    - 0x0103 `MGMT_ACTOR_SIG`（署名 blob）
        
    - 0x0201 `PAY_FI_ID`（文字列）
        
    - 0x0202 `PAY_ACCOUNT_ID`（ASCII/IBAN/国内様式）
        
    - 0x0203 `PAY_AMOUNT_MINOR`（i64 8B；通貨最小単位）
        
    - 0x0204 `PAY_CCY_NUM`（u16：ISO4217 numeric）
        
    - 0x0205 `PAY_TRACE_ID`（文字列/UUID）
        
    - 0x0206 `PAY_LEDGER_PREHASH`（32B）
        
    - 0x0207 `PAY_LEDGER_POSTHASH`（32B）
        
    - 0x1001 `SIG_MGMT`（管理側Ed25519署名）
        
    - 0x1002 `SIG_PAY`（決済側Ed25519署名）
        
    - 0x1F01 `AUDIT_NOTE`（UTF-8）
        
    - 0x1F02 `ERR_CODE`（u16）/ `ERR_DETAIL`（文字列）
        
- **Flags**: bit0=必須、bit1=暗号化済み（追加ISE層）、他予約
    
- **Length**: Value長（BE）
    

> **管理TLV** と **決済TLV** はそれぞれ独立したTLV列。  
> WNは**必須TLV**を検証し、不足/破損で `SOURCE_MISSING`/`INVALID` を返す。

---

## 3) 署名とハッシュ規約（検証順序）

1. **AEAD**: GCMで暗号完全性を先に担保（TAG検証 NG→即破棄）
    
2. **ISE復号**（鍵系列はKMS/TPM）
    
3. **ヘッダ整合**: `FrameMagic/Version/HeaderLen/PayloadLen`
    
4. **冪等キー `H` 再計算**: `SHA3-256(TxID‖Timestamp_ISE)` 一致必須
    
5. **TLV必須セット検証**
    
    - 管理: `MGMT_ENTITY_ID` + `MGMT_DOC_HASH` + `SIG_MGMT`（Flags必須）
        
    - 決済: `PAY_FI_ID` + `PAY_ACCOUNT_ID` + `PAY_AMOUNT_MINOR` + `PAY_CCY_NUM` + `SIG_PAY`
        
6. **署名検証**
    
    - `SIG_MGMT` は `MGMT_ENTITY_ID‖MGMT_DOC_HASH‖TxID‖Timestamp_ISE` のハッシュに対する署名
        
    - `SIG_PAY` は `PAY_*核要素‖TxID‖Timestamp_ISE` のハッシュに対する署名
        
    - ハッシュは **BLAKE3-256** 推奨（高速・実運用向き）
        
7. **会計整合**
    
    - `PAY_LEDGER_PREHASH` → `PAY_LEDGER_POSTHASH` が**借貸一致**で遷移可能か
        
    - 金額 `i64`（マイナス許容/返金）＋ `ISO4217 numeric` の対応表
        
8. **結果確定**
    
    - 合格: `RECONCILE_OK` → 正規化レコード生成（下記3.1）
        
    - 否決: `RECONCILE_MISMATCH`/`SOURCE_MISSING` 等 → poison-queue
        

---

## 4) 正規化レコード（WN→DB）固定ヘッダ（48B）

|オフセット|長さ|名称|型|説明|
|---|---|---|---|---|
|0|4|`NormMagic`|ASCII|`"TCLN"`|
|4|1|`NormVer`|u8|0x01|
|5|1|`Status`|u8|0=OK, 1=MISMATCH, 2=MISSING, 3=DUP, 4=INVALID|
|6|2|`NormFlags`|bitfield|監査/留保フラグ|
|8|8|`TxID`|u64|継承|
|16|8|`Timestamp_ISE`|u64|継承|
|24|32|`H`|256bit|冪等キー|

- この後ろに**正規化ボディ（TLV）**を連結。DBは `H` UNIQUE で**冪等吸収**。
    

---

## 5) ルーティング/再送/ACK（最小）

- **ACKの向き**: **DB→WN→MQ**（下流→上流のみ）
    
- **再送トリガ**: 上流の**未ACK検知**（TTL＋指数バックオフ）
    
- **冪等**: DBは `INSERT OR IGNORE`（UNIQUE(H)）で二重吸収し、**常にACK**を返す
    

---

## 6) ビット/境界・整列ルール

- すべて **Big-Endian**。
    
- フィールドは**自然境界に整列**（u16=2B, u32=4B, u64=8B）。
    
- TLVは **4B境界**に前詰め（必要なら 0x00 パディング）。
    
- 署名・ハッシュは **生バイト**（base64禁止）で格納。
    

---

## 7) セキュリティ鍵系列（要点）

- **KMS鍵ID** は外枠ヘッダとは別に **MetaTLV** に `KMS_KEY_ID`（文字列）で入れる。
    
- **TPMハンドル** は `TPM_SEAL_HANDLE`（u32）で明示可。
    
- **鍵解決順**: KMS（AES）→KMS（ISE鍵）→TPM（必要時）
    
- WNは **KMS_REQUIRED/TPM_REQUIRED** を `HeaderFlags` で確認して分岐。
    

---

## 8) エラーコード（`ERR_CODE` TLV / u16）

- `0x0000` OK
    
- `0x0001` `SOURCE_MISSING_MGMT`
    
- `0x0002` `SOURCE_MISSING_PAY`
    
- `0x0003` `RECONCILE_MISMATCH`
    
- `0x0004` `INVALID_SIGNATURE`
    
- `0x0005` `LEDGER_INCONSISTENT`
    
- `0x0006` `KMS_UNAVAILABLE`
    
- `0x0007` `TPM_UNAVAILABLE`
    
- `0x0008` `DECRYPT_FAIL`
    
- `0x0009` `SCHEMA_INVALID`

## 9) 最小実装チェックリスト

-  外枠64Bヘッダ→GCM AAD同期
    
-  `H=SHA3-256(TxID‖Timestamp_ISE)` 冪等キー一貫
    
-  内枠32Bヘッダ→TLV連結（Mgmt/Pay/Meta）
    
-  必須TLV検証＋署名復号（Ed25519/BLAKE3-256）
    
-  会計整合（借貸一致、金額型=i64、ISO4217 u16）
    
-  正規化レコード48B＋TLV→DB、`UNIQUE(H)`
    
-  ACK連鎖（DB→WN→MQ）、再送は上流起点
    
-  すべてBig-Endian、4B境界、署名は生バイト

## ✅ MQが持つべき理由（技術的根拠）

### 1. トランザクション生成の起点がMQ

- MQは「管理機関側入力」「決済機関側入力」の**双方を受け取りペア化**する。
    
- その時点で両者の主体情報を解決（`InternalID` 付与）しなければならない。

### 2. 更新頻度が極低

- 主体は「組織／機関／金融口座／契約主体」など、日次更新以下。
    
- 基本的には**月次または年度更新単位**で十分。
    
- よって**静的リードDB**（`sqlite` or `rocksdb`）で完全に賄える。
    

### 3. ISE署名の整合点

- MQで署名範囲を確定させる際に、「誰」の内部IDを固定長で確定。
    
- WN／DB側はこのIDを再解決せず比較するのみ。
    
- 署名の安定性＝辞書の静的性に依存するため、更新を避けることが整合的。
    

### 4. 責任分界

- 「誰」という情報は**個人情報／KYC情報**に該当する可能性があり、  
    DBやWNが持つのはリスク。
    
- MQは業務的に“フロント寄り”（リクエスト受付層）であり、  
    この位置にKYC辞書を配置するのが法的・監査的にも自然。

## ✅ 1. AES-256-GCM の場合

- **鍵長**：256 bit（32 B）固定。
    
- **Nonce/IV**：96 bit（12 B）固定。
    
- **TAG**：128 bit（16 B）固定。
    

AES-GCM の安全性は  
`key ⊕ iv ⊕ plaintext → ciphertext` の確定的計算に依存し、  
鍵をハッシュ化しても暗号強度は上がりません。  
むしろ KDF (Key Derivation Function) 以外のハッシュ混入は冗長。

したがって

- KMS または TPM が返す生の 32 B バイナリ鍵をそのまま使用、
    
- `hash(key)` のような再演算は不要。

## ✅ 2. ISE（恭順暗号）の場合

ISE は非可逆構造であり、  
暗号核は「**ランダマイザ**」と「**構造化テーブル**」によって出力が決定します。  
つまり：

`ISE(data, rand) → signature`

であって、  
`rand` そのものが**鍵であり、ハッシュ化できない確率変数**。

- すでにバイナリ形式（例：128〜256 bitのランダマイザ列）で一意。
    
- ハッシュすると確率空間が縮み、逆に衝突確率を上げてしまう。
    
- ISEの「シグネチャ整合性検証」は、鍵を直接比較すれば十分。
    

→ よって、ISE鍵もハッシュ不要。

### 処理ルール

1. **小数点を整数化**

2. **ボイド間交換禁止**
    
    - `From.AssetCode & 0x8000 == To.AssetCode & 0x8000 == 1` の場合 → 拒否。
        
3. **ステーブル⇄ボイド間交換**
    
    - `From.AssetCode & 0x8000 != To.AssetCode & 0x8000` の場合のみ許可。
        
    - Exchange ノードが `ExchangeFlag = TRUE` をセット。
        
4. **金銭的価値ゼロ**
    
    - `AmountMinor` はゼロであっても署名整合対象。
        
    - 記録は残るが会計影響ゼロ。
