## 実装パターン（具体／技術的）

### A. デコイ生成（データ別パターン）

- **構造化データ（会計／在庫）**
    
    - フォーマット保持（FPE: Format-Preserving Encryption）で値域を保ったまま擬似値化。
        
    - 統計整合：本当の分布（平均・分散・相関）を維持するために、カーネル密度推定→サンプリングを使う。
        
    - 決定論的鍵（KDF）により「同一入力→同一デコイ」を保証（改竄検出容易化）。
        
- **半構造化データ（ログ／メッセージ）**
    
    - 正規表現ベースでトークン化（日時・ID・金額等を分離）、各トークンを独立にデコイ化して再結合。
        
- **非構造化（文書／画像）**
    
    - 文書：NLPベースの書き換え（語彙置換＋センチメント維持）。
        
    - 画像：GAN ベースの合成（顔/物体は差分置換）。
        
- **物理測定値（ワクチン量・受領回数）**
    
    - μ,σ といった統計パラメータを維持する小乱数（加算ノイズ）＋符号化（万倍固定点）で不可逆に近づける。ただし現地検証と紐付けるための受領トークンは別途管理。
        

### B. 「署名をISEする」＝署名レイヤの設計

- 基本フロー：
    
    1. 原データ D に対して通常の署名 S = Sign_SK(D) を生成。
        
    2. ISE 変換 T を S に作用させ、S' = ISE(T, S, meta) を生成。meta にはデコイポリシー等を埋める。
        
    3. S' を台帳（Witness）に刻印。S' 単体では「本物の署名かどうか」を判別できない（＝DB抜きで真実確認不可）。
        
    4. 真実を開示する際は、M-of-N で T の復号鍵または解読シードを開示→S を再現／検証。
        
- 推奨手法（実装オプション）：
    
    - **レダクタブル署名 / redactable signatures**：署名の一部を公開／隠蔽できるようにする。
        
    - **可選開示対応ゼロ知識証明（ZK）**：S が D に対して正当であることを、D の内容を明かさず証明。
        
    - **閾値署名（Threshold Sig）＋M-of-N HSM**：復元には複数ステークホルダの承認を必須に。
        

### C. データの水平／垂直管理（運用スキーマ）

- **水平（シャーディング）**：業務／領域単位でノード分割。各シャードは独自のトークン化鍵を持つ（KDF派生）。
    
- **垂直（列／フィールドレベル）**：個人識別情報（PII）や決済関連は別領域でABE（属性ベース暗号）で暗号化。権限に応じて異なる属性キーを配布。
    
- **アクセス制御**：
    
    - 公開：集計（L1） → 集計は差分プライバシー適用。
        
    - 監査：L2 → 監査用キーで選択的復号（ログは不可逆ではないが、復号操作はM-of-Nで記録）。
        
    - 原票：L3 → M-of-N + 物理立会い + HSMプロシージャ。

## A) 苗字（surname） — テーブル撹乱（あなた案）

`K_perm = HKDF(master_key, "surname-perm-v1") perm_index = DeterministicPermIndex(K_perm, surname)   # HMAC-DRBG→index if not exists SurnameTable[perm_index]:     SurnameTable[perm_index] = CreateDecoyRecord() record.surname_ptr = perm_index store(record)`

ポイント:

- `DeterministicPermIndex` は同一苗字で同じ index を返す（整合性保持）。
    
- SurnameTable 自体は別シャードで保存し、復号には M-of-N 承認が必要。

## B) 名前（given name） — DB全体スワップ

**方針**: 名前フィールド群は、保存時にテーブル全体のランダムスワップを行い、同一DB抜取でも対応するエントリをすぐに見つけられないようにする。

擬似処理:

`K_swap = HKDF(master_key, "name-swap-v1") perm = DeterministicPermutation(K_swap, N)  # 長さNの置換 name_index = perm[sequential_id_for_record] record.name_ptr = name_index store(record)`

運用:

- `N`（スワップブロックサイズ）は運用により調整（例: 10kレコードブロック単位）。

## C) 住所（numbers reversible, names swap）

**方針**:

- 数字部分（郵便番号・番地等）= 可逆暗号（AES-GCM）
    
- 地名部分 = スワップまたはトークン化（決定論的トークン）  
    擬似処理:
    

`addr_num_cipher = AESGCM_Enc(K_addr_num, numeric_part, AAD=context) K_loc_perm = HKDF(master_key, "loc-perm") loc_token = DeterministicToken(K_loc_perm, textual_place_name) record.addr = {num: addr_num_cipher, place: loc_token}`

留意:

- 数字は復号で正確値が得られる（法令要求や配送で必要）。
    
- 地名は統計的整合を維持するためトークン化で代替（例: TOK_483）。

**方針**: 可逆暗号に加え「形式的整合性（チェックデジット）」を保つため、FPE（FF1）で満たす。

`cipher_value = FF1_Enc(K_fpe, plain_value, tweak) store(cipher_value)`

# 4) 署名→ISE ラッピング（簡潔プロトコル）

1. 通常の電子署名 `S = Sign(SK_entity, hash(D))` を生成。
    
2. ISE トランスフォーム `S' = ISE_Transform(S, policy_meta, seed)` を作成（例: S' = Enc_AEAD(K_ise_wrap, S || meta) XOR mask(seed)）。

## 1) 4 系統インデックスの作り方（安全かつ衝突回避）

- `idx_i = HMAC_DRBG(K_perm, surname || context || salt_i) mod N_shard` を i=0..3 で4回生成。
    
    - `salt_i` を固定長で分けることで**同姓は同じ一群にまとめつつ**索引分散を担保。
        
    - 決定論的なので再現性あり（※必要なら照合用トークンは別に持つ）。
        
- 衝突問題は確率論で扱う（4つあれば誤判別率は微小）。重い衝突対応はバケットチェーンで処理。
    

## 2) テーブル更新（sudo update 相当）──安全且つアトミックに

- 更新は `signed manifest` を作る：バージョン、ハッシュ、サイズ、公開鍵署名。
    
- ノードは manifest 検証後に **atomic swap**（temp file → rename）で差替え。ロールバック可能。
    
- 運用はローリング（全ノード同時ではなく）で、万一の回帰を速やかに可能に。
    

## 3) 圧縮／実行時展開の現実的運用

- 名前テーブルは辞書圧縮が効くので **zstd**（高圧縮＋高速解凍）推奨。LZ4は超高速だが圧縮率下がる。
    
- 実行時：メモリマップ（mmap）＋on-demand展開でI/Oを最小化。
    
- ノードリソースが厳しければ「圧縮ブロック単位」で部分展開（ブロックキャッシュ）。

- ミドルネーム／ローカル表記は別カラムで地域別シャード保持。

## 6) 鍵と暗号（量子耐性の実装方針）

- 現行：`data → AES-256-GCM`、鍵は KMS/HSM で管理（既存）。
    
- 量子備え方：**ハイブリッド鍵交換**を採る。
    
    - KEM(post-quantum, e.g. CRYSTALS-Kyber) でセッション鍵を得つつ、従来のKEX（EC）と併用して互換性確保。
        
    - 暫定運用は「KEM + AES-256」＝ AES の鍵を KEM で包む形（移行に最も現実的）。
        
- 将来：AES の置換ではなく、**鍵流通レイヤを PQC 化**しておけば本体暗号は入れ替え容易。

# 設計原理（1行）

# 高水準アーキテクチャ

- データ保存 = `ISE_WRAP( Sign(SK_entity, hash(D)) , policy_meta, pepper )` を台帳へ刻印。
    
- `pepper` は HSM に分散保管（M-of-N）。HSMなしで `ISE_UNWRAP` は不可能か、極端にコストを増す仕様にする。
    
- 各レコードに「**N_decoy** 個の本物らしい代替候補 (honey outputs)**」を組み込みる（Honey-encryptionの思想）。
    
- 攻撃者が DB を丸ごと持ち出しても、**キー無しで真偽を突き止めるためには** argon2id (大メモリ設定)×大量ループ を通さねばならない。
    

合法性・運用上のポイント：正当監査は HSM + M-of-Nで短時間復元。悪意ある者は HSMなしで検証を試みる→コスト爆発。

# 実装パターン（具体）

## 1) ハニー／ISE ハイブリッド（必須）

- 各データ D に対して：
    
    1. 通常署名 `S = Sign(SK, H(D))` を生成。
        
    2. `seed = HKDF(K_pepper, H(D) || meta)` を生成（`K_pepper` は HSM/M-of-N）。
        
    3. `honey_candidates = HoneyGen(seed, N_chaff)` を作る（デコイ文字列群、統計的に本物と区別不可）。
        
    4. 真の出力位置 `i_true` は `seed` により決定され、台帳には `Enc_AES(K_record, concat(i_true || S || meta))` を置くが **ISE変換**でさらにラップしておく（ISEはレイヤ化したラップ関数）。
        
- 盗み出し時：攻撃者は `honey_candidates` と暗号文群を持つが `K_pepper` が無ければ `i_true` の位置は不明。`i_true` を突き止めるには `seed` を再現するしかない → `seed` の復元は KDF brute-force 必須。
    

## 2) 計算コスト増幅（KDF戦術）

- `seed` の導出に Argon2id(salt, time_cost=..., mem_cost=...) を使い、`K_pepper` の候補空間に対する各試行のコストを巨大化する。
    
- 具体パラメータ（参考）：Argon2id time_cost = 4、mem_cost = 1 GiB、parallelism = 4。
    
    - 1試行あたり ≈ 1GBメモリを確保し、数秒〜数十秒を要する（ノード性能に依存）。
        
    - 攻撃者が GTA（グローバルGPUアレイ）で並列化しても、大量の候補を総当たりするには現実的時間外（days→years）を要するように調整する。
        
- さらに：`seed` を derive する際に`N_rounds`を入れて多重KDF（Argon2id の内外で）し、ワンパスで済まないようにする。
    

> 理念：正当者は HSM で `K_pepper` を直接利用して即復元、第三者は Argon2id 総当たりでしか判定できない（高コスト）。

## 3) 大量デコイ（chaff）生成と分布整合

- HoneyGen は単純に乱数で作るのではダメ。**統計的整合（語彙分布・長さ・フォーマット）**を維持すること。N_chaff を大きく（例 1024～65536）しておくほど攻撃側コストが上がる。
    
- 実装：学習済み軽量生成器（NLP小型モデル＋テンプレート＋統計サンプリング）で各レコードに N_chaff を作る。デコイ群は台帳にあるが位置は暗号化。
    
- 空間コントロール：全レコードで同じ N_chaff にするより、ランダム化して攻撃者の推測（本物は大抵 N_small）を困難にする。
    

## 4) 検証（整合性チェック）を「計算的に重く」する方法

- 典型：検証に seed を要し、seed の再構築は大KDF brute-force。
    
- 追加：検証過程に**一方向チェーン連鎖**を導入（リプレイが使えない）。例：検証は chain_of_hashes[i] を総なめに走査する必要があり、chain の長さ L を大きくすることで検証コスト＝O(L) にする。だが正当者は HSM 内で chain anchor を持つため O(1)で復元可能。
    
- もう一段：検証に**メモリ集約的なグラフ検証**（Cuckoo graphやballoon hashingの派生）を入れる。攻撃者は巨大メモリを要求され、クラウドでの短時間並列化が困難になる。
    

## 5) 運用での「短絡（fast path）」

- 正当監査ルート＝HSM(M-of-N)で K_pepper を出して短時間で検証。
    
- 監査ログ・復元操作は Witness に全記録（不可逆の証跡）を刻印する。これで正当者の行為も公開可能だが、鍵はHSMにある限り外部は無理。

# 具体パラメータ提案（即使える）

> 目標：攻撃者が 1 レコードの本物位置を突き止めるのに 2^40 相当のコストを要求する（現実的に不可能）

- N_chaff = 4,096（各レコードにつき4096候補）

# 1) 基本デザイン（多重ISEの概念図）

データ `D` の保存フロー（高レベル）：

1. 正常署名を作成：`S0 = Sign(SK_entity, H(D))`
    
2. 署名とメタを束ねてバンドル：`B0 = {D_meta, S0, H(D)}`
    
3. 多重ISEラップを行う（ここで n = 3 ）：
    
    - `L1 = ISE_WRAP(B0, policy1, pepper1)`
        
    - `L2 = ISE_WRAP(L1, policy2, pepper2)`
        
    - `L3 = ISE_WRAP(L2, policy3, pepper3)`
        
4. 台帳に刻印：`Store( L3 )`
    
5. 監査時は M-of-N により `pepper3` → `ISE_UNWRAP(L3)` → 得られる `L2` を再度 `pepper2` で解除 … 最後に `S0` を復元して `Verify(S0, H(D))` を行う。
    

ポイント：`policy_i` と `pepper_i` は **HSM分割で保管**。台帳（DB）には `L3` のみ。どの層が本物位置を握るか等は台帳から分からない。

---

# 2) ISE_WRAP の構成（実装仕様）

各ラップは次の処理を含める：

- 1. **データ正規化**：固定表現にする（canonicalization）
        
- 2. **Salt/Nonce 組合せ生成**
        
    
    - `salt_i = HMAC(master_salt, context || layer_index)`（master_salt は HSM）
        
- 3. **KDF（メモリハード）**（任意でレイヤ差）：
        
    
    - `k_i = Argon2id(PepperInput || salt_i, mem=Mi, time=Ti, parallel=Pi)`
        
    - ここで `PepperInput` は HSM からのシードで、外部に出さない。
        
- 4. **ラップ操作**（例の一実装）：
        
    
    - `enc = AES-GCM-Enc(k_i.enc, payload_i)`
        
    - `mask = HMAC(k_i.mac, metadata_i)`
        
    - `wrapped = enc XOR mask` （XORは任意。ISE特性で複数操作を混ぜる）
        
    - 最後に `ISE_meta_i = {layer_index, mac_tag, argon_params_hash}` を付与 **だが** この `ISE_meta_i` は台帳には最小化し、全体のエンベロープのみ置く（攻撃者が層数を容易に推定できないようにする）。
        

重要：`pepper_i`（実際のKDFシード）はHSMに分散。各層で別KMS/別HSMグループを使うことを推奨（地理分散）。

---

# 3) 層ごとの非公開メタデータ（攻撃者に見せない）

台帳に残すのは最小情報（L3バイナリ＋公開タイムスタンプ＋不可逆ハッシュ）。  
`{ argon_params, layer_index }` 等の素直なメタは**HSM内メタ**として持ち、台帳には付けない。  
そのため攻撃者は「これが第何層目のISEか」も推定できない。

---

# 4) 鍵管理・閾値設計（必須）

- 各 `pepper_i` は別の HSM クラスタに分割（n_i = 7, m_i = 4 等、層ごとに可変）。
    
- 復元（ISE_UNWRAP）は **M-of-N HSM呼び出し＋物理立会い** を必須にする。
    
- HSMは FIPS L3/4、遠隔ロック・地理冗長・監視ログ強化。
    
- 監査での復元は Witness に不可逆ログ（誰が、いつ、どのHSMで、どの鍵を開けたか）を刻印。
    

---

# 5) 計算負荷戦術（攻撃者側コストを階層的に爆発させる）

設計原則：

- 層ごとに **KDFパラメータを増幅**（例：L1: Argon2id mem=512MB time=2、L2: 1GB time=4、L3: 2GB time=6）。
    
- ラップを剥がすには層を順に試すしかなく、各層で KDF を通すコストが掛かる。
    
- さらに、各層の `seed` は `HKDF` 等で上層依存にする（L2 の seed = HKDF(K_pepper2, L1_digest)）→層横断での候補数が指数増。
    

結果：

- 攻撃者は「候補空間 × (コスト_L1 + cost_L2 + ...)」を総当たり。パラメータ調整で現実不可能に出来る。
    
- 正当者は HSM により O(1) で `k_i` を得て解除。
    

---

# 6) 「層数が隠蔽される」仕組み

- 台帳はただの opaque blob（L3）。内部構造（ラップ回数・各層パラメータ）は HSM のメタデータでのみ保持。
    
- 復元プロシージャは HSM内部で `verify` を逐次呼び、外部には「成功/失敗」のみ返す。外部は何層剥がれたか知らない。
    
- このため攻撃者は「いくつ剥がさないといけないか」すら分からず、全層を総当たりするしかない。
    

---

# 7) 署名保持者だけが真偽を証明する仕組み（フロー）

1. 保存時に `S0` を生成してISEでラップ。
    
2. 真偽確認要求：主体（署名保持者）が M-of-N を満たし HSM にアクセス → HSM内で L3→L2→L1 を解除し `S0` を復元 → `Verify(S0, H(D))` を内部で実施。
    
3. HSM は検証結果（真/偽）と監査ログを Witness に刻印して外部に返す。**真の値（D）そのものは外部に出さない**ことも可能（たとえば「整合性OK」だけを返す）。
    

これで「署名保持者しか真偽を証明できない」ことが実現される。

# 8) パフォーマンス考慮（実運用）

- 多重ISEは復元時にHSMアクセスが複数回発生するため HSMコストが上がる（だが正当運用は頻度が低い）。
    
- 保存（ライト）は層分のISE_WRAPを行うためやや遅いがバッチ化可。
    
- 監査（UNWRAP）は頻度を絞る（監査の際のみ）。普段は L3 の opaque 集計のみで運用。
    
- レイテンシ要件があるユース（リアルタイム決済など）は、ISEを「監査用別路」にして本稼働データはライトに保つ設計も可能（ただし透明性は劣る）。

## 要点（超短縮）

1. **鍵短周期ローテーション（Batch Keying）**：例）1,000レコード毎に新鍵。鍵は一時しか有効にしない。
    
2. **鍵そのものをISEで複数層ラップ**：鍵 = `ISE_WRAP_n(...ISE_WRAP_2(ISE_WRAP_1(k)))`。復元には M-of-N HSM／閾値が必須。
    
3. **鍵の識別情報を台帳に残さない**：台帳は opaque blob。どの鍵で暗号化されたか外部推定不可。
    
4. **鍵交換は署名付き manifest＋Witness 刻印**：更新は署名された manifest（ハッシュ）で行うが manifest は鍵の中身を明かさない。
    
5. **短周期・小ロットでの運用**により、盗まれた DB は「大量の鍵候補 × 多層ISE × chaff」によって意味を失う。
    
6. **正当復元は HSM 閾値で O(1)**。悪意ある者は総当たりで現実的に不可能。

## 運用原則（推奨、すぐ導入できる）

- **Batch size**：1,000（運用負担とセキュリティのバランス）
    
- **鍵ライフ**：発行から使い切り（そのバッチの承認後は即ロック）
    
- **鍵階層**：RootKey（極秘；HSM分散保管） → Day/Batch Key（ISEラップ） → RecordKey（派生）
    
- **鍵復元**：M-of-N HSM（物理立会い、監査ログ、WORM刻印）
    
- **監査証跡**：すべての鍵発行・復元操作を Witness に刻印（不可逆ログ）
    
- **鍵漏洩時対策**：鍵を盗まれても「どの鍵がどのレコードに対応するか分からない」ため侵害効果は極小化。

## すぐ使える PoC（Python）

apply ISE wraps sequentially: L1(L2(L3(batch_key)))     payload = batch_key     metas = []     for pepper, params in zip(peppers, layer_params_list):         wrapped, meta = ise_wrap(payload, pepper, params)         metas.append(meta)         payload = wrapped     return payload, metas  def unwrap_key_multi_ise(wrapped_blob: bytes, peppers: list, layer_params_list: list):     payload = wrapped_blob     # reverse order for unwrapping     for pepper, params in reversed(list(zip(peppers, layer_params_list))):         payload = ise_unwrap(payload, pepper, params)     return payload  # --------- simulate attacker cost (naive) ---------- def attacker_bruteforce_estimate(chaff_count, per_try_time_sec):     # # 実装パターン（短く）

1. **関数境界を厳密化**：ISE_WRAP/ISE_UNWRAP のシグネチャを `fn wrap_layer(input: Secret<Vec<u8>>, params: &LayerParams, hsm: &HsmHandle) -> WrappedBlob` のように `Secret<>` を入れる。
    
2. **レイヤごとのポリシー型**：`struct LayerParams { mem_kib: usize, time: u32, parallel: u32, salt: [u8;16] }` を明示。
    
3. **鍵は HSM で生成・分割**：ローカルで乱数を持たせない。HSM トークン経由で `pepper_i` をリクエスト。
    
4. **IO は最小化**：平文はできるだけ HSM 内で扱い、ユーザー空間には `Secret` として短時間しか残さない。
    
5. **多重ISE を直列で実行**：各層は独立パラメータで KDF を行い、AES-GCM でラップ。復元は逆順。
    
6. **ログは最小公開**：成功/失敗とタイムスタンプだけ台帳に出す。原票解放は M-of-N と立会いでのみ。

# 短い Rust スニペット（雛形）

`use secrecy::{Secret, ExposeSecret}; use zeroize::Zeroize; use aes_gcm::{Aes256Gcm, aead::{Aead, KeyInit, OsRng, rand_core::RngCore}}; use argon2::{Argon2, Params as ArgonParams};  pub struct LayerParams {     pub mem_kib: u32,     pub time: u32,     pub parallelism: u32,     pub salt: [u8;16], }  pub struct WrappedBlob(Vec<u8>);  pub trait Hsm {     // returns a layer-specific pepper (Secret)     fn fetch_pepper(&self, layer_id: u8) -> Secret<Vec<u8>>;     fn attest_action(&self, action: &str); }  // simple ISE layer wrap pub fn ise_wrap_layer(hsm: &dyn Hsm, payload: Secret<Vec<u8>>, params: &LayerParams, layer_id: u8) -> WrappedBlob {     // get pepper from HSM (thresholded in real world)     let pepper = hsm.fetch_pepper(layer_id);     // derive key via Argon2 (mem in KiB)     let argon = Argon2::new(argon2::Algorithm::Argon2id, argon2::Version::V0x13,                             ArgonParams::new(params.mem_kib, params.time, params.parallelism, None).unwrap());     let mut out = [0u8; 32];     argon.hash_password_into(pepper.expose_secret(), &params.salt, &mut out).unwrap();     // AES key     let key = aes_gcm::Key::from_slice(&out);     let cipher = Aes256Gcm::new(key);     // nonce     let mut nonce = [0u8;12];     OsRng.fill_bytes(&mut nonce);     let ciphertext = cipher.encrypt(&nonce.into(), payload.expose_secret().as_ref())         .expect("encrypt");     // zeroize sensitive temporarily     out.zeroize();     // pack nonce|ciphertext     let mut blob = vec![];     blob.extend_from_slice(&nonce);     blob.extend_from_slice(&ciphertext);     hsm.attest_action("ise_wrap");     WrappedBlob(blob) }  // unwrap similarly (use HSM fetch_pepper and Argon2 derive)`
